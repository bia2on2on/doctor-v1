## 1. Goals, non-goals, honest threat model

### 1.1 Goals
- G1. A real, cryptographically verifiable license document for CPMS 1.0, upgradeable later to the full product line without data loss.
- G2. A commercial/contractual value model: the signed document is the license; the plugin verifies it locally.
- G3. Activation that works for a **phone-only owner** and a customer with no GitHub knowledge (offline first; online optional).
- G4. No path in which a 1.0 customer is left without an activation route.
- G5. Safety floor: patient records remain viewable in every stage; an issuer outage never locks stored patient data or critical access; login and the offline activation/renewal path remain reachable. Ordinary expiry follows only the Stage 1/2/3 action matrix in §7; after T1, clinical/business-record writes are limited to finishing a qualifying Visit opened before T1, while license activation/renewal and the read/login/backup/export safety paths remain available.

### 1.2 Non-goals
- N1. Preventing edits of shipped plugin PHP. The repository and the ZIP are public/readable; anyone may fork and remove the gate.
- N2. Hiding PHI. The license payload carries no PHI (ADR-0028); this is a control-plane document.
- N3. Implementing a central license service, billing, activation counting, revocation UI, or update-plane changes. Those are outside this document (ADR-0023 §7 marks them FUTURE/OPEN).
- N4. Any schema change (see §10).

### 1.3 Honest threat model (public code base)
- **What the signature stops:** a forged or altered document. An attacker cannot mint a document that verifies under the trusted public-key ring, cannot change `expires_at`, `install_id`, `domain`, `entitlements`, `key_id`, and cannot reuse another installation's document where the signed claims are checked (`LicenseService.php:318-339`, `:407-425`).
- **What the signature does NOT stop:** editing the plugin code — all PHP is public, so an attacker can patch out the gate. No code secrecy is claimed. The economic value is commercial/contractual (a valid signed document is what the customer pays for; support, renewal, updates and entitlements ride on it).
- **Threats accepted:** local gate tampering; clock manipulation (§6.2, a real limitation); cloning a site to another `install_id`; mass document sharing. Mitigations are contractual + signed binding + (future) server-side activation counting, not obfuscation.
- **Secrets boundary:** only public verification keys ship. No secret, token, password or key material belongs in the repo, this PR, CI logs, the ZIP or this document (§3).
- **Known-unfixed-code note (no exploit detail):** the shipped public-key ring is empty and the legacy placeholder is invalid, so every activation attempt fails closed today (§7.4, D1). That is a release blocker, not a vulnerability to exploit.

### 2.2 Canonical serialization and signature
- Reuse the existing verifier: `canonicalJson()` recursively `ksort`s and `json_encode`s with `JSON_UNESCAPED_UNICODE` (`LicenseSignature.php:34-39`); verification is `sodium_crypto_sign_verify_detached` over exactly that byte string with the selected Ed25519 public key (`:119-143`). Detached Ed25519 is the reference behaviour: <https://doc.libsodium.org/public-key_cryptography/public-key_signatures>; PHP binding: <https://www.php.net/manual/en/function.sodium-crypto-sign-verify-detached.php>.
- Fail-closed: if `sodium` is unavailable the document is "not verifiable" and activation is refused (`LicenseSignature.php:24-27,131-133`).
- Any issuer tooling MUST produce the canonical byte string from the same rules (sorted keys, unescaped Unicode, no whitespace) or verification fails; the document that the customer pastes is exactly the JSON the issuer signed.

### 2.3 Format versioning
- `schema_version` must be the integer `2`; any other value, or only one of `schema_version`/`key_id`, fails closed (`LicenseSignature.php:56-67,97-106`).
- Legacy (unversioned) documents keep the existing legacy path and never fall back from v2 (`LicenseSignature.php:75-89`). No `schema_version=3` is designed; `DOCUMENT_SCHEMA_VERSION = 2` stays unchanged.

## 3. Keys and custody

### 3.1 Generation outside the repository
- Generate an Ed25519 key pair once, on a device the owner controls, **outside** this repository and outside CI. Only the base64 public key is copied into the shipped `LicenseKeys` ring; the private key never enters the repo, the plugin, the database, the ZIP or any log.
- Current placeholders are intentionally invalid: `LicenseKeys.php:23` (`REPLACE_AT_RELEASE_WITH_ED25519_PUBLIC_B64`) and the empty ring `LicenseKeys.php:31` (`TRUSTED_PUBLIC_KEYS_B64 = []`). Release-manifest keys are a separate key (`ReleaseKeys.php:16`); do not reuse one key for both (ADR-0029 separation).

### 3.3 Explicitly rejected
- **Rejected:** storing the signing key in GitHub Actions secrets or any CI. In a public repository, fork pull requests and workflow logs are real exposure paths; a key that can sign license documents must not be reachable from CI. Reference: <https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions>.
- Rejected: repo files, `.env`, commits, issues/PRs, unencrypted cloud notes, email/chat, the plugin ZIP, the database, committed `wp-config.php`, and any "test key" left in shipped source.
- Commercial release builds reject test/dev keys (§3.5). The owner-approved **internal TEST ZIP** is a separately named, access-controlled, noncommercial test artifact with no real key; it is not a bypass flag or a commercial/release ZIP and may never be sold or publicly published.

### 3.4 Key id and rotation (F2)
- `key_id` is a bounded ASCII identifier, not key material: `is_valid_key_id()` requires a leading letter and `[A-Za-z0-9._-]*`, ≤64 chars (`LicenseKeys.php:107-111`; the file ends at `:112`). The trusted ring maps `key_id => base64 public key`, at most 32 entries, and a malformed or oversized ring is rejected **as a whole** (`LicenseKeys.php:33-34,62-89`). Selection is an exact lookup: an unknown or malformed `key_id` returns `null` and verification fails (`LicenseKeys.php:94-102`, `LicenseSignature.php:97-106`).
- **Correction (F2):** a document's `key_id` must **already be trusted by the installed plugin**. "A fresh `key_id` per document" is wrong and would make every such document unverifiable. Rotation order is therefore: (1) add the new public key under its new `key_id` to the ring and ship a plugin release; (2) only after customers can install that release, start issuing documents signed by the new private key; (3) keep the old public key until no still-installed version needs it; (4) remove it in a later release. Two keys can be trusted at once by design.
- **Lost or compromised key — recovery path (L1, K3).** Recovery material must be delivered **inside a new authenticated plugin ZIP**: generate a replacement pair, add its public key under a new `key_id`, and ship a replacement ring. The compromised fingerprint must be in the gate's denylist and the compromised key must be absent from the legacy constant, release-manifest key and v2 ring; see §3.5. The customer installs the replacement ZIP through the still-open channel (§4.3) and reactivates with a new signed document through the always-available offline form. A removed-key document becomes `INVALID` on re-verification (§7.5); this does not erase records or revoke the Stage 3 right to finish a qualifying active Visit, but it does not restore unrestricted writes. **Data preservation on package overwrite is UNKNOWN** until a build-time upgrade test proves it (WordPress `Plugin_Upgrader::install()`: <https://developer.wordpress.org/reference/classes/plugin_upgrader/install/>). Reconstructing a lost private key is impossible. Revocation under a newly trusted key is possible only after the replacement ring is installed; until then, an already issued document remains valid according to its signed claims.
- **Release invariant (gate criterion, §3.5):** the ring must hold **at least two independent public keys** (primary + backup, generated and held separately) so a single loss or compromise does not strand every install. The M3 conditions are decided (§3.6); the concrete signing method and independent custody for each key remain open owner items (§3.6.3 and §12/D3).

### 3.5 Release-build gate — MANDATORY for commercial releases; internal TEST ZIP exception (M2)

- OBSERVED at base `main`: `bin/build-release.sh:109-120` has a content-policy self-check but no production-key/placeholder gate. The gate below is a required future implementation; this document does not claim it exists.
- **Commercial release:** gate is mandatory, runs for every commercial ZIP, has no skip flag/environment bypass, and failure stops publication. The owner or release operator runs it on an owner-controlled machine; CI must hold no signing secret. Only public-key fingerprints are handled.
- **Internal TEST ZIP exception (owner-approved, rev 11):** this is not a commercial release. It must use a distinct internal-only build target and conspicuous artifact label; it may omit real production keys for install/upgrade tests, makes no official version change, is never sold and is never published publicly. It must not create a general `--skip-gate` path. The ordinary content-policy checks and clear separation from production artifacts still apply. No implementation of this exception is present in this docs-only revision.
- **Commercial-build inputs:** two owner-supplied files outside the repository/CI: an expected SHA-256 fingerprint list for every shipped public key and a denylist of test/dev key IDs and values. Missing/malformed files fail with `KEYLIST_MISSING`; overlap fails with `KEYLIST_OVERLAP`.
- **Commercial PASS criteria — all required:**
  1. Legacy and release-manifest public-key constants contain no placeholder and strictly decode using `base64_decode($s, true)` (`LicenseSignature.php:134-139`; PHP manual: <https://www.php.net/manual/en/function.base64-decode.php>), round-trip canonically (`base64_encode($decoded) === $input`), and decode to exactly 32 bytes (Ed25519; <https://doc.libsodium.org/public-key_cryptography/public-key_signatures>). Failure reasons, in order: `PLACEHOLDER`, `BAD_BASE64`, `NON_CANONICAL_BASE64`, `PUBKEY_LENGTH`.
  2. The trusted v2 ring contains **2–32** entries; every value passes the same decode/round-trip/length checks; decoded key bytes are pairwise distinct. Failure reasons include `KEY_COUNT`, `RING_SIZE`, `DUP_KEY`.
  3. Every `key_id` is unique and matches `^[A-Za-z][A-Za-z0-9._-]{0,63}$` (`LicenseKeys.php:107-111`); fail `KEY_ID_FORMAT`.
  4. First check expected-list/denylist overlap; then, for each shipped legacy, manifest and ring key, check denylist before expected-list membership. A denylisted fingerprint fails `DENYLISTED_KEY`; a non-denylisted key missing from the expected set fails `UNEXPECTED_KEY`. A recovery build must receive the compromised fingerprint as an explicit recovery input, require it in the denylist or fail `RECOVERY_DENYLIST_MISSING`, and ensure it is absent from every shipped public-key position. Release source contains neither `tests/` nor generated private-key material.
  5. ZIP manifest lists exactly the files; recorded SHA-256 matches the artifact (`build-release.sh:99-101`).
  6. ZIP version, build argument/`CPMS_VERSION`, and update-manifest version agree (`build-release.sh:23,99-101`).
  7. Existing content-policy check passes (`build-release.sh:109-120`).
- **Exact commercial failure line:** `BUILD FAILED: license/release key gate: <CHECK> failed (<detail>)` on stderr; non-zero exit; no ZIP published. `<CHECK>` includes `PLACEHOLDER`, `BAD_BASE64`, `NON_CANONICAL_BASE64`, `PUBKEY_LENGTH`, `KEY_COUNT`, `RING_SIZE`, `DUP_KEY`, `KEY_ID_FORMAT`, `KEYLIST_MISSING`, `KEYLIST_OVERLAP`, `DENYLISTED_KEY`, `UNEXPECTED_KEY`, `RECOVERY_DENYLIST_MISSING`, `MANIFEST_MISMATCH`, `VERSION_MISMATCH`, and `CONTENT_POLICY`.
- **RELEASE-STOP:** any listed failure. The gate cannot prove private-key possession or independent custody of the two private keys; those remain process controls (§3.6.3).
- **T-L32 (future test definition):** one independent failing fixture per reason; `DENYLISTED_KEY` and `UNEXPECTED_KEY` must stay distinct; test legacy, release-manifest and ring locations independently. `BAD_BASE64` uses a character outside the alphabet; `NON_CANONICAL_BASE64` uses input that strict-decodes but fails `base64_encode($decoded) === $input` (including whitespace if the supported runtime skips it); `PUBKEY_LENGTH` uses a clean decode of the wrong byte length. php-src currently skips ASCII whitespace even in strict mode, while the PHP manual does not resolve whitespace handling; confirm on the supported runtime and assert decode failure and round-trip failure separately.

### 3.6 OWNER DECISION M3 — signing, conformance, outage behaviour (binding)

**Binding owner decision (recorded 2026-11-17):** (1) real Ed25519 signatures; (2) private key only at the license issuer, never repo/CI/plugin/customer site; (3) plugin stores public key(s) only and verifies offline; (4) a temporary issuer outage does not lock patient data or critical access; (5) the licensing mechanism sends no patient data to a central server. This is a binding target requirement, not an observed online-flow guarantee: the current activation form forwards unvalidated `license_key` text, so §3.6.1 limits what is established. Per-customer manual signing is the initial path; an activation website/server is optional and later. Offline activation is required. No trusted third-party signer has been identified.

**Earlier owner decisions retained or superseded by revision 12:** the internal TEST ZIP exception remains as specified in §3.5; handwriting is allowed in Stage 2 for eligible existing care and after T1 only for a qualifying Visit under §7.2; the prior broad “all handwriting on every existing Visit in every license state” wording is superseded. Likewise, the earlier M1 promise that every existing appointment may be checked in in every state is superseded: under the Q3 recommendation, a pre-T0 appointment may be admitted only during Stage 2 (ending immediately before T1), and first admission at/after T1 is denied unless a qualifying Visit already exists. Q3 awaits owner decision; see §7.2-7.4. These expiry limits do not remove the safety floor (records view, activation, or the safe-finish path).

## 5. Domain binding

- Canonicalization is the single existing seam: lower-case and strip one leading `www.`; scheme/path/port and IDN/punycode are out of scope; never `HTTP_HOST` (`LicenseDomain.php:24-32`, `LicenseService.php:380-388`). The UI prerequisite in §8.1 must display exactly this canonical value.
- A mismatch turns a **permissive** outcome into `RESTRICTED`/`binding_mismatch`; restoring the bound domain restores the normal state with the document untouched.
- **Correction (F7):** the mismatch does **not** always win. `applyDomainBinding()` returns the computed outcome unchanged when it is already self-blocking and is not ordinary expiration (`LicenseService.php:415-417`, `isSelfBlocking()` `:432-441`). So `SUSPENDED`, `REVOKED`, `INVALID` and stale `UNREACHABLE` keep their own (more severe) state and reason — the code's own severity order is `RESTRICTED` 4 < `UNREACHABLE` 5 < `INVALID` 6 < `SUSPENDED` 7 < `REVOKED` 8 (`LicenseStatus.php:116-131`) — while `ACTIVE`, `EXPIRING`, `GRACE` and `RESTRICTED`/`expired` are converted to `binding_mismatch`. This is the single severity rule; §7.5 specifies the same outcome for future stored-payload re-verification.
- Staging/clones: a staging host is a different canonical domain and needs its own document, or the owner omits the `domain` claim (`LicenseService.php:408-410`). Clones share the source `install_id` only when the whole database is copied (§7.5).
- Domain change and re-binding: a reissue is a new signed document with a new `domain`; reissue counts and one-active enforcement are commercial/policy controls (future central service), not code. The signed `activation_id` claim is the intended hook (`LicenseSignature.php:107-112`).

## 6. Time, stages and offline operation

### 6.1 Exact T0/T1 boundaries

- **T0** is the signed integer Unix `expires_at`, interpreted as an exact UTC instant at second precision. Authorization uses server-side UTC time; browser time, clinic/location timezone and Jalali display do not affect the license stage.
- **T1** is one Gregorian calendar month after T0 in UTC, computed directly from T0: advance year/month by one, preserve hour/minute/second, and set day to `min(day(T0), days-in-target-month)`. Examples: 2028-01-31 12:34:56Z → 2028-02-29 12:34:56Z; 2027-01-31 → 2027-02-28 at the same time. Do not use 30 days, local timezone, DST, or chained month additions. `DateTimeImmutable` is suitable for deterministic date calculations (<https://www.php.net/manual/en/class.datetimeimmutable.php>).
- The intervals are half-open and have no grace/skew extension: **Stage 1** iff `now < T0`; **Stage 2** iff `T0 <= now < T1`; **Stage 3** iff `now >= T1`. T0 itself is Stage 2; T1 itself is Stage 3. The `EXPIRING`/`GRACE` labels never defer either boundary.
- A valid signed document with an ordinary expiry uses T0/T1 even if its displayed state is still `EXPIRING` or `GRACE`, or has become `RESTRICTED`/`expired`. Missing T0, invalid signature, binding mismatch, revocation, suspension, stale unreachable, or first-run-window exhaustion is not assigned a fabricated T0/T1; see §7.5.

### 6.2 Offline behavior and clock rollback

- Ordinary verification is offline. A cached verified signed document controls expiry; refresh failure is not invalidity and cannot change `expires_at`, manufacture T0, move T1, delete records, hide activation, or require a network call on every page request.
- **Clock rollback LIMITATION (verified at `LicenseStateMachine.php:116-145`):** the current code clamps only a future activation-window start and has no persisted high-water mark. Rolling back the server clock can postpone T0/T1 evaluation. The existing skew value does not bound the delay; it only affects status presentation (`LicensePolicy.php:28`; `LicenseStateMachine.php:85-91`).
- **Optional proposal P-AR (no schema; owner approval needed):** persist `max(observed now)` in a WordPress option (e.g. `cpms_license_last_seen`) and compute `effective_now = max(now, stored)` for activation-window and stage evaluation. This is a speed bump, not DRM: a database/filesystem administrator can edit/delete it; a restore can move it backwards; and a mark last written before expiry cannot guarantee T0 is reached. Rollback detection must never remove records, activation, backup/export or the safe-finish path. The existing tests must not claim P-AR is implemented.

### 6.3 Update rights are a separate plane

`update_rights_until` and the update entitlement govern the update plane only. They neither move T0/T1 nor grant or revoke a clinical operation; adding/removing the claim must leave the same clinical stage decision. An expired commercial term may still have an independently valid update right under the existing update policy. Stage-specific clinical authorization is evaluated separately, with persisted Visit/appointment context where required (§7).

### 7.4 Fresh install, empty keys and non-expiry adverse states

- A fresh install without a signed document has no T0/T1. It enters `ACTIVATION_PENDING` through the existing seven-day cutoff, then becomes `RESTRICTED` with reason `activation_window_expired`; the pre-F10 migration route has 30 days then `migration_grace_expired` (`LicenseStateMachine.php:116-145`; `LicensePolicy.php:29-30`). Preserve those current durations until the owner changes D4. A Visit already open at the last allowed instant of the window remains finishable while active. No new booking, patient enrollment or walk-in starts after the cutoff under this fallback.
- After the cutoff, continue record viewing, login, backup/export, offline activation/renewal and safe completion of an already-open Visit. An appointment without a Visit is not permission to start care after the cutoff. On a fresh install, backup restore remains an open safety interface; it must not reset the current activation-window clock or copy another install's authority.
- The production source currently has an invalid legacy public-key placeholder (`LicenseKeys.php:21-23`) and empty v2 trusted ring (`:25-34`). Legacy documents fail verification; a v2 document cannot resolve its key id (`LicenseKeys.php:62-101`; `LicenseSignature.php:97-106,119-143`). UI reachability is not activation capability. M2 blocks commercial publication until real keys are installed and the gate passes; the internal TEST ZIP is never a customer route.
- Binding mismatch, invalid signature, revocation, suspension and stale unreachable are not ordinary signed expiry. They retain distinct fail-closed new-business outcomes; do not assign them a synthetic T0/T1 or silently call an issuer outage a revocation. In every such state, preserve records view, login, offline activation/renewal, backup/export and the safe-finish exception for an already persisted active Visit. They do not permit new appointment admission or an independent Visit.
- Explicit `DEVELOPMENT` mode is a separate, visible test override, not a default/hidden production bypass. `NOT_CONFIGURED`, `ACTIVATION_PENDING` and `ACTIVATION_GRACE` follow the first-run window, not signed-expiry stages.

### 7.5 Stored payload trust and restore (OBSERVED limitation; future prerequisite)

- **OBSERVED:** `currentState()` reads stored `payload_json`, computes local state and reapplies domain binding (`LicenseService.php:74-82,359-364,407-425`). The stored signature is not re-verified on every read; `install_id` is checked at activation (`:323`) rather than each state read. This is a local integrity limitation, not permission to delete/hide records or remove activation/safe-finish access.
- **Future re-verification prerequisite:** check signature, `install_id` and canonical domain at least once per request, caching only for that request. Preserve distinct outcomes: bad signature → `INVALID`; `install_id` mismatch → `INVALID`; domain mismatch → `RESTRICTED`/`binding_mismatch`; an already self-blocking computed state (`SUSPENDED`, `REVOKED`, `INVALID`, stale `UNREACHABLE`) is preserved. This does not expand the Stage 2/3 permissions or remove the safety floor.
- Binding mismatch, signature invalidity, revocation, suspension, stale unreachable and activation-window expiry remain distinct from ordinary expiry. Their new-business rules fail closed; records remain viewable and the activation route and eligible safe-finish path remain available. Renewal must install a real signed document.
- Restore onto a new install is an open interface because the restore design is not established in base `main`. Stage 3 default is no restore; Stage 1/2 restore remains subject to normal RBAC but must not reset the effective activation clock, bypass signed-domain/install binding or make a tampered stored payload authoritative. Resolve rebind and license-row preservation under S-1 before implementing this exception. No schema or restore hook is introduced here.

Risk if deferred: a restored site may need manual reactivation; a careless restore can undermine expiry enforcement.

If any required write path cannot prove a Visit/appointment relation using persisted server-side data, do not accept a caller flag or silently add a column: fail closed and return to S-1/owner approval.
  - **OPEN (S-2, M3) — concrete signing workflow.** The five M3 conditions are **DECIDED** (§3.6): Ed25519, private key only at the issuer, public-key-only offline validation, no outage lock of patient data/critical functions, no patient data to any server by the licensing mechanism. The concrete workflow, key generation/backup custody, issuer hosting, revocation and outage operations remain open (§3.6.3); the decision-ready comparison is a proposal only. Risk if deferred: no signing path is approved, so D1 cannot be completed and 1.0 cannot ship a verifiable document.

## 11. Impact on the 1.0 → Full upgrade path

- The license tables are **shared** between 1.0 and the full line. This design adds no table/column, so nothing in 1.0 must be undone at upgrade; a 1.0 install with a valid document continues to verify in the full line under the same ring.
- Migration rule: new migration numbers are decided in the **full line first** and copied byte-identical to 1.0; 1.0 never creates a migration absent from the full line. This design creates **no** migration, so it is compatible by construction.
- Data-loss safety: the document, `install_id` and activation window persist across the upgrade; the offline path and the public-key ring are unchanged, so a 1.0 customer always keeps an activation route.
- **Entitlements — corrected (F9, K5).** Today `hasFeature()` returns false for an **absent** feature **and for a present feature whose value is `false`**; an unknown feature supplied as `true` is accepted (`EntitlementRegistry.php:29-37,49-53`), while `limitOf()` returns `null` for an unknown or absent limit and `allowsCreation()` then returns **true** (`:58-76`) — an unknown limit is silently *unlimited*. **Design requirement:** the set of limit keys is a closed allowlist defined in code with an explicit default per key; a document may only *narrow* those defaults; unknown keys are ignored (never treated as a grant) and logged; a missing known key takes its code default (never "unlimited"). The same rule applies to features: a document can only enable features the code knows. `LicenseSignature.php:107-117` is the signed-metadata grammar (`activation_id` bounded id, `update_rights_until` positive int) — it is **not** an entitlement extension hook; entitlements are interpreted only by `EntitlementRegistry`. Update rights remain a separate plane and never override the §7 Stage 1/2/3 clinical matrix.

### Revision-12 expiry policy questions (recommendations are not owner approvals)

- **Q1. Stage 2 new-patient records and patient self-enrollment.** Options: (a) block all new patient rows and self-enrollment from T0 until immediately before T1 (recommended); (b) allow only verified self-enrollment during Stage 2, still denying it at T1. Stage 3 remains read-only for new patient creation under either choice. The former one-/six-month windows are retired, not a Stage 3 option. **Manager assumption/recommendation:** (a), pending owner confirmation. It is simple and avoids client-asserted returning status, but a returning patient cannot create a new local record during Stage 2. Appointment continuity is only for appointments already linked to a patient row before T0.
- **Q2. Walk-in Visit without a booked appointment during Stage 2.** Options: (a) block at T0 (recommendation; a walk-in creates a new Visit); (b) allow during Stage 2 and block new walk-in admission at T1. A Stage 2 walk-in allowed under (b) must be a server-created persisted Visit; if it remains active at T1, only the normal safe-finish exception applies after T1. Stage 3 blocks new walk-ins under either option. The possible urgent-care impact must be explicitly accepted before implementation.
- **Q3. A confirmed pre-T0 appointment not yet admitted at T1.** Options: (a) deny first admission at/after T1 unless a qualifying Visit row already exists (recommendation; matches the durable Visit boundary); (b) explicitly approve a finite exception for first admission of that pre-T0 appointment in Stage 3. Option (b) does not move T1, extend Stage 2 or create a general grace period: it is a bounded Stage 3 exception to the pre-T1 Visit-only rule, not automatic eligibility from a reservation. Before approval, specify the finite admission cutoff and exactly which Visit/care-completion writes, cancellation and refund rules apply, then add separate tests.
- **Q4. Stage 3 refund and disaster-restore exceptions.** Recommendation: strict read-only for patient/business-record mutations after T1—no historical refunds or restore; only operations required to finish a qualifying active Visit remain allowed, while the control-plane and safety paths in §7 remain available. Option: permit a privileged, audited historical refund and/or disaster-recovery restore after T1. Pros: supports exceptional legal/accounting recovery; cons: broadens the read-only exception and can mutate closed records. Resolve with S-1 before implementation.
