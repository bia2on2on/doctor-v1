## 1. Goals, non-goals, honest threat model

### 1.1 Goals
- G1. A real, cryptographically verifiable license document for CPMS 1.0, upgradeable later to the full product line without data loss.
- G2. A commercial/contractual value model: the signed document is the license; the plugin verifies it locally.
- G3. Activation that works for a **phone-only owner** and a customer with no GitHub knowledge (offline first; online optional).
- G4. No path in which a 1.0 customer is left without an activation route.
- G5. Hard safety rule (H1): license state must never block clinical reads, existing appointments, **check-in of an existing appointment**, visit completion, payments on existing invoices, backup/export/restore, or OTP verification.

### 1.2 Non-goals
- N1. Preventing edits of shipped plugin PHP. The repository and the ZIP are public/readable; anyone may fork and remove the gate.
- N2. Hiding PHI. The license payload carries no PHI (ADR-0028); this is a control-plane document.
- N3. Implementing a central license service, billing, activation counting, revocation UI, or update-plane changes. Those are outside this document (ADR-0023 §7 marks them FUTURE/OPEN).
- N4. Any schema change (see §10).

### 1.3 Honest threat model (public code base)
- **What the signature stops:** a forged or altered document. An attacker cannot mint a document that verifies under the trusted public-key ring, cannot change `expires_at`, `install_id`, `domain`, `entitlements`, `key_id`, and cannot reuse another installation's document where the signed claims are checked (`LicenseService.php:318-339`, `:407-425`).
- **What the signature does NOT stop:** editing the plugin code — all PHP is public, so an attacker can patch out the gate. No code secrecy is claimed. The economic value is commercial/contractual (a valid signed document is what the customer pays for; support, renewal, updates and entitlements ride on it).
- **Threats accepted:** local gate tampering; clock manipulation (§6.5, a real limitation); cloning a site to another `install_id`; mass document sharing. Mitigations are contractual + signed binding + (future) server-side activation counting, not obfuscation.
- **Secrets boundary:** only public verification keys ship. No secret, token, password or key material belongs in the repo, this PR, CI logs, the ZIP or this document (§3).
- **Known-unfixed-code note (no exploit detail):** the shipped public-key ring is empty and the legacy placeholder is invalid, so every activation attempt fails closed today (§7.2, D1). That is a release blocker, not a vulnerability to exploit.

### 2.2 Canonical serialization and signature
- Reuse the existing verifier: `canonicalJson()` recursively `ksort`s and `json_encode`s with `JSON_UNESCAPED_UNICODE` (`LicenseSignature.php:34-39`); verification is `sodium_crypto_sign_verify_detached` over exactly that byte string with the selected Ed25519 public key (`:119-143`). Detached Ed25519 is the reference behaviour: <https://doc.libsodium.org/public-key_cryptography/public-key_signatures>; PHP binding: <https://www.php.net/manual/en/function.sodium-crypto-sign-verify-detached.php>.
- Fail-closed: if `sodium` is unavailable the document is "not verifiable" and activation is refused (`LicenseSignature.php:24-27,131-133`).
- Any issuer tooling MUST produce the canonical byte string from the same rules (sorted keys, unescaped Unicode, no whitespace) or verification fails; the document that the customer pastes is exactly the JSON the issuer signed.

### 2.3 Format versioning
- `schema_version` must be the integer `2`; any other value, or only one of `schema_version`/`key_id`, fails closed (`LicenseSignature.php:56-67,97-106`).
- Legacy (unversioned) documents keep the existing legacy path and never fall back from v2 (`LicenseSignature.php:75-89`). No `schema_version=3` is designed; `DOCUMENT_SCHEMA_VERSION = 2` stays unchanged.

## 3. Keys and custody

### 3.1 Generation outside the repository
- Generate an Ed25519 key pair once, on a device the owner controls, **outside** this repository and outside CI. Only the base64 public key is copied into the shipped `LicenseKeys` ring; the private key never enters the repo, the plugin, the database, the ZIP or any log.
- Current placeholders are intentionally invalid: `LicenseKeys.php:23` (`REPLACE_AT_RELEASE_WITH_ED25519_PUBLIC_B64`) and the empty ring `LicenseKeys.php:31` (`TRUSTED_PUBLIC_KEYS_B64 = []`). Release-manifest keys are a separate key (`ReleaseKeys.php:16`); do not reuse one key for both (ADR-0029 separation).

### 3.2 Phone-only signing and recovery — four evaluated workflows (OWNER DECISION M3)
Signing an Ed25519 document is a computation: it cannot be done by hand, in a chat app, or in a photo. The four candidate classes requested by the owner are evaluated below. **Nothing here is claimed to exist in this repository; no key material may be stored in the repo or CI; every UNKNOWN must be confirmed on the owner's own device before the first paid document.** "Loss" = the key becomes unusable; "compromise" = an attacker can sign.

| # | Workflow | Prerequisites | Money / time | Limits | Loss impact | Compromise impact | Key-loss recovery | Practicality (phone-only, no domain) |
|---|---|---|---|---|---|---|---|---|
| W1 | **Phone terminal environment** — Android Termux + PHP CLI (sodium) or Python/PyNaCl; iOS has no general terminal | Android phone; Termux from its official source; `php` with sodium or `python`+`pynacl`; the key file copied from the generation device; a short issuer script (not shipped here) | ≈ $0; setup 1-3 h, then ~5 min/document | No hardware isolation; the key is a readable file; clipboard handling; package availability on the exact device/OS is **UNKNOWN** | Phone loss/theft = key loss unless an offline backup exists; restore or rotate (§3.4) | Malware/foreground app that reads storage or the clipboard can exfiltrate the key; rotate immediately | Restore the key file from the offline backup; else new pair + ship new public key + reissue | **Medium** on Android; **LOW/UNKNOWN** on iOS |
| W2 | **Trusted technical partner or second device holding the key** | A person/device the owner trusts; a working signer on it; a safe channel for document + signature | Possible compensation; coordination per document | Key outside the owner's sole control; partner availability; the partner's device security | Partner's copy lost = rotate | Partner's device compromised or insider misuse = forged documents; rotate | Partner re-issues, or rotate + reissue | **High if a trusted partner exists**, but adds a third party and contradicts sole custody |
| W3 | **Offline hardware key or separate offline machine** — YubiKey PIV (firmware 5.7+, Ed25519 algorithm E0) or OpenPGP ed25519 (sign/auth only), or an air-gapped spare phone/laptop | A token that performs *raw* Ed25519 over arbitrary bytes (most FIDO2 keys do not) plus PKCS#11/OpenPGP tooling, or a spare air-gapped device with PHP/Python; OTG/NFC to the phone | Token ≈ $25-70 or spare device ≈ $50-150; setup 1-3 h | Key never leaves the device (good); not all tokens support arbitrary Ed25519; the phone needs OTG/NFC | Device loss = backup seed/second device or rotate | Very low: no exportable key; theft needs the PIN; rotate if the PIN is compromised | Backup seed/second device, or rotate + reissue | **Medium** (Android OTG/NFC); **UNKNOWN** on iOS; the air-gapped spare machine avoids phone tooling |

**OWNER DECISION M3 (binding; recorded 2026-11-17):** the five M3 conditions are decided — see §3.6. This table is the evidence for the concrete workflow choice, which remains an **open owner item (§3.6.3 U1)**; it is not a ranking — the choice stays with the owner. Every UNKNOWN must be confirmed on the owner's own device. Whichever workflow is chosen, it requires at least one offline key copy and a written rotate-on-loss procedure (§3.4). The decision-ready comparison is §3.6.3.

### 3.3 Explicitly rejected
- **Rejected:** storing the signing key in GitHub Actions secrets or any CI. In a public repository, fork pull requests and workflow logs are real exposure paths; a key that can sign license documents must not be reachable from CI. Reference: <https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions>.
- Rejected: repo files, `.env`, commits, issues/PRs, unencrypted cloud notes, email/chat, the plugin ZIP, the database, committed `wp-config.php`, and any "test key" left in shipped source.
- Test keys are generated only inside tests and must be rejected by the release build (§3.5).

### 3.4 Key id and rotation (F2)
- `key_id` is a bounded ASCII identifier, not key material: `is_valid_key_id()` requires a leading letter and `[A-Za-z0-9._-]*`, ≤64 chars (`LicenseKeys.php:107-111`; the file ends at `:112`). The trusted ring maps `key_id => base64 public key`, at most 32 entries, and a malformed or oversized ring is rejected **as a whole** (`LicenseKeys.php:33-34,62-89`). Selection is an exact lookup: an unknown or malformed `key_id` returns `null` and verification fails (`LicenseKeys.php:94-102`, `LicenseSignature.php:97-106`).
- **Correction (F2):** a document's `key_id` must **already be trusted by the installed plugin**. "A fresh `key_id` per document" is wrong and would make every such document unverifiable. Rotation order is therefore: (1) add the new public key under its new `key_id` to the ring and ship a plugin release; (2) only after customers can install that release, start issuing documents signed by the new private key; (3) keep the old public key until no still-installed version needs it; (4) remove it in a later release. Two keys can be trusted at once by design.
- **Lost or compromised key — real recovery path (L1, K3).** If the only trusted key is lost or compromised, no document signed by a key the install already trusts exists, so the recovery material must be delivered **inside a new plugin ZIP**: generate a new pair, add its public key under a new `key_id` to the ring, ship a normal release per the order above, and the customer installs the replacement ZIP by the normal plugin-replacement route (channel is an open decision, §4.3). **The replacement ring must NOT contain the compromised key** — not as the legacy `LicenseKeys::PRODUCTION_PUBLIC_B64` (`:23`), not as `ReleaseKeys` (`:16`), and not in the v2 ring (`:31`); the §3.5 gate enforces this against the run-time denylist. **Authenticated ZIP delivery is a REQUIREMENT** (the update manifest is signed by `ReleaseKeys`, ADR-0029), but the channel itself is not chosen here (D2). After replacement, stored documents are **re-verified against the new ring**: a document signed by the removed key fails verification and the state becomes `INVALID` (§7.5), so the customer re-activates with a document signed by the new key through the always-available offline form — **no clinical lock** (H1/M1 stay in force). **Data preservation on package overwrite is UNKNOWN** until a build-time test proves it (WordPress `Plugin_Upgrader::install()`: <https://developer.wordpress.org/reference/classes/plugin_upgrader/install/>). What is **impossible**: reconstructing the lost private key. Revoking an already-issued document of a compromised key is possible **only after** the replacement ring is installed (a signed `revoked`/`suspended` document under a newly trusted key); before that, such documents stay valid until expiry.
- **Release invariant (gate criterion, §3.5):** the ring must hold **at least two independent public keys** (primary + backup, generated and held separately) so a single loss or compromise does not strand every install. The M3 conditions are decided (§3.6); the concrete signing method for each key is an open owner item (§3.6.3 U1).

### 3.5 Release-build gate — MANDATORY, exact criteria (M2)
- Today `bin/build-release.sh` runs a content-policy self-check (`:109-120`) but has **no** key/placeholder check (OBSERVED). The gate below is a build-policy change for a later PR; this document fixes its criteria.
- **Who runs it / cannot be skipped:** the owner or a designated release operator, on a machine the owner controls (or CI holding **no** signing secret). **No flag, no environment bypass**; it runs on every release build and a failure stops the build. Only **public-key fingerprints** are ever handled; no private key is present.
- **Run-time key material (outside the repo and CI):** the operator supplies two owner-held files, both produced outside the repo and CI and never committed: (a) an **expected list** of sha256 fingerprints of every allowed base64 public key, and (b) a **denylist** of known test/dev `key_id`s and key values. The gate **FAILS if either file is absent or malformed** (`KEYLIST_MISSING`) and **FAILS if the two lists intersect** (`KEYLIST_OVERLAP`).
- **PASS criteria — every one must hold or the build stops:**
  1. `LicenseKeys::PRODUCTION_PUBLIC_B64` (`:23`) and `ReleaseKeys::PRODUCTION_PUBLIC_B64` (`:16`) contain no `REPLACE_AT_RELEASE` substring **and** each passes the **same strict decode as the verifier** — `base64_decode($s, true)` (`LicenseSignature.php:134-139`; PHP strict mode: <https://www.php.net/manual/en/function.base64-decode.php>), failing with **`BAD_BASE64`** — **and** the round-trip `base64_encode($decoded) === $input` holds, failing with **`NON_CANONICAL_BASE64`** — **and** the decoded length is exactly `SODIUM_CRYPTO_SIGN_PUBLICKEYBYTES` = 32 bytes, failing with **`PUBKEY_LENGTH`** (Ed25519 public key, <https://doc.libsodium.org/public-key_cryptography/public-key_signatures>). The three decode checks run in that order, so each failure has its own reason.
  2. The ring `LicenseKeys::TRUSTED_PUBLIC_KEYS_B64` (`:31`) holds **≥2 and ≤32** entries (`MAX_TRUSTED_PUBLIC_KEYS`, `:34`; a larger ring is rejected as a whole by the loader, `:72-73`); every value passes the same three decode checks as criterion 1 (`BAD_BASE64`, `NON_CANONICAL_BASE64`, `PUBKEY_LENGTH`) and is exactly 32 bytes; the decoded key bytes are **pairwise distinct** (no duplicate key under two `key_id`s).
  3. Every ring `key_id` matches `^[A-Za-z][A-Za-z0-9._-]{0,63}$` and is unique (`LicenseKeys.php:107-111`).
  4. **Fingerprint check (able to fail), with a defined precedence:** the build-level `KEYLIST_OVERLAP` check runs first and fails the whole build if the two lists intersect; then, for each shipped key (legacy, release-manifest and ring) the **denylist is checked FIRST** — a fingerprint present in the denylist fails with its **own** reason **`DENYLISTED_KEY`**; only if it is not denylisted is expected-list membership checked, and absence there fails with **`UNEXPECTED_KEY`**. The two reasons are distinct and never collapse into one. For a **recovery build** (a rebuild whose purpose is to revoke a compromised key), the compromised key's fingerprint **MUST also be present in the denylist**, and the gate **FAILS with `RECOVERY_DENYLIST_MISSING`** otherwise; the same check applies in all three shipped locations. Release source must contain no `tests/` and no generated key material.
  5. ZIP manifest/hash: `<name>-<version>-manifest.txt` (`build-release.sh:99`) lists exactly the ZIP files and the recorded `.sha256` (`:100-101`) equals the actual digest.
  6. Version consistency: ZIP version = `CPMS_VERSION` (`build-release.sh:23`) = update-manifest version.
  7. The existing content-policy self-check passes (`:109-120`: no forbidden files; required runtime SDK/autoload present).
- **Exact failure message:** `BUILD FAILED: license/release key gate: <CHECK> failed (<detail>)` on stderr, exit non-zero; `<CHECK>` ∈ {`PLACEHOLDER`, `BAD_BASE64`, `NON_CANONICAL_BASE64`, `PUBKEY_LENGTH`, `KEY_COUNT`, `RING_SIZE`, `DUP_KEY`, `KEY_ID_FORMAT`, `KEYLIST_MISSING`, `KEYLIST_OVERLAP`, `DENYLISTED_KEY`, `UNEXPECTED_KEY`, `RECOVERY_DENYLIST_MISSING`, `MANIFEST_MISMATCH`, `VERSION_MISMATCH`, `CONTENT_POLICY`}. No ZIP is published on failure.
- **RELEASE-STOP conditions:** any of the above failures. A stop is not overridable in CI; the owner fixes the source and rebuilds.
- **LIMITATION:** the gate proves the shipped public keys are well-formed, distinct, expected and not denylisted; it **cannot prove that any holder controls the corresponding private key, nor that the ≥2 keys are independently controlled** (custody/process properties, §3.2, §3.6).
- **Negative tests (T-L32) — independent failing cases, each asserting its OWN distinct `<CHECK>` reason, and each fixture constructed so that only the rule under test can fail** (so a missing check cannot hide behind another): `PLACEHOLDER`; `BAD_BASE64` (strict decode fails: a character genuinely outside the Base64 alphabet, e.g. `!` or `@`) and `NON_CANONICAL_BASE64` (strict decode succeeds but `base64_encode($decoded) !== $input`: embedded whitespace — space, `\t`, `\n`, `\r` — or a non-canonical padding/encoding variant such as an omitted `=`) — each asserted **independently** on a legacy key, on a release-manifest key and on a ring key; `PUBKEY_LENGTH` (decodes cleanly but ≠ 32 bytes) on all three; `DUP_KEY`; `KEY_COUNT` (<2 ring keys); `RING_SIZE` (>32); `KEY_ID_FORMAT`; `KEYLIST_MISSING` (expected list absent, then denylist absent); malformed expected list, then malformed denylist; `KEYLIST_OVERLAP`; `DENYLISTED_KEY` — a shipped key whose fingerprint IS in the denylist (the compromised fingerprint) and is absent from the expected list, so the lists stay disjoint and `KEYLIST_OVERLAP` cannot fire; asserted **separately** in all three shipped locations and kept distinct from the `UNEXPECTED_KEY` case (same key absent from the expected list, denylist empty); `UNEXPECTED_KEY` (shipped key absent from the expected list); `RECOVERY_DENYLIST_MISSING` with the compromised fingerprint tested in all three shipped locations; `MANIFEST_MISMATCH`, `VERSION_MISMATCH` and `CONTENT_POLICY` — one independently asserted negative case each.
- **PHP strict-decode fact (Q1):** OBSERVED in php-src `ext/standard/base64.c` (strict loop): whitespace (space 32, `\t` 9, `\n` 10, `\r` 13) maps to `-1` and is **skipped even when `$strict` is true**, so it does **not** fail strict decode; bytes outside the alphabet map to `-2` and fail (`BAD_BASE64`), as do a truncated final group and a wrong padding count — so those are strict-decode cases, not round-trip cases. INFERENCE: this holds for the PHP build that ships; the build-time test (T-L32) must confirm it on the target runtime, and the suite must fail if either the strict decode or the round-trip check is missing. The php.net manual wording ("return false if the input contains character from outside the base64 alphabet") does not by itself settle whitespace, hence the test.

Current check (OBSERVED `LicenseService.php:318-339`): `product` match, `install_id` match, `license_id` non-empty, `expires_at > 0`, and `expires_at >= issued_at` only when `issued_at > 0`; `issued_at`/`expires_at` are cast with `(int)`; **no comparison with "now"** — a correctly signed, already-expired document is accepted and stored. A non-integer `issued_at` is cast silently: if the cast is **positive** it still takes part in the ordering, and only a cast ≤ 0 skips it.
Required future check (implementation prerequisite, with tests in §9):
- A1. Reject `expires_at <= now + maxClockSkew` (already-expired document). Honest note: this **does** reject a retroactive document **and also some still-future expiries** that fall inside the skew window, so the owner must always issue a document whose `expires_at` is comfortably in the future; an install that currently holds an expired document is in the same restricted region either way, so nothing is lost that a valid renewal would not restore.
- A2. Reject non-integer or non-positive `issued_at`/`expires_at` (strict `is_int`, no silent cast) and `issued_at > now + maxClockSkew` (future-issued).
- A3. Keep `expires_at >= issued_at`; optionally reject documents whose lifetime exceeds an owner-set maximum.
- A4. Keep the signature check last and unchanged (`LicenseService.php:334-335`).
Rejections use the existing generic `CLINIC_LICENSE_INVALID` code and never disclose which field failed to the browser (it may be logged locally without values).

## 5. Domain binding

- Canonicalization is the single existing seam: lower-case and strip one leading `www.`; scheme/path/port and IDN/punycode are out of scope; never `HTTP_HOST` (`LicenseDomain.php:24-32`, `LicenseService.php:380-388`). The UI prerequisite in §8.1 must display exactly this canonical value.
- A mismatch turns a **permissive** outcome into `RESTRICTED`/`binding_mismatch`; restoring the bound domain restores the normal state with the document untouched.
- **Correction (F7):** the mismatch does **not** always win. `applyDomainBinding()` returns the computed outcome unchanged when it is already self-blocking and is not ordinary expiration (`LicenseService.php:415-417`, `isSelfBlocking()` `:432-441`). So `SUSPENDED`, `REVOKED`, `INVALID` and stale `UNREACHABLE` keep their own (more severe) state and reason — the code's own severity order is `RESTRICTED` 4 < `UNREACHABLE` 5 < `INVALID` 6 < `SUSPENDED` 7 < `REVOKED` 8 (`LicenseStatus.php:116-131`) — while `ACTIVE`, `EXPIRING`, `GRACE` and `RESTRICTED`/`expired` are converted to `binding_mismatch`. This is the single severity rule; §7.5 states the same rule for the stored-payload path and does not contradict it.
- Staging/clones: a staging host is a different canonical domain and needs its own document, or the owner omits the `domain` claim (`LicenseService.php:408-410`). Clones share the source `install_id` only when the whole database is copied (§7.5).
- Domain change and re-binding: a reissue is a new signed document with a new `domain`; reissue counts and one-active enforcement are commercial/policy controls (future central service), not code. The signed `activation_id` claim is the intended hook (`LicenseSignature.php:107-112`).

## 6. Time, states and offline operation

- T0 = signed `expires_at`. The state machine yields `ACTIVE → EXPIRING → GRACE → RESTRICTED` (`LicenseStateMachine.php:47-100`); `EXPIRING` starts one expiry-grace before T0 (`:93-97`, `LicensePolicy.php:24`); `GRACE` is T0 + skew … T0 + grace + skew (`:85-91`).
- Grace does not move T0: the gate checks the signed `expires_at` **before** the status shortcut (`SignedLicenseGate.php:47-48`). Renewal simply supersedes the stored row; a renewed document with a later `expires_at` restores full function immediately, with no destructive local lock (ADR-0023 §0).
- Fully offline within the licensed period: no network call on ordinary page loads; the last verified document governs, and `UNREACHABLE` is distinct from `INVALID` (`LicenseStateMachine.php:71-75`). The offline document path is always available while the trusted public key is valid.
- **Clock rollback — corrected (F4, L5).** Revision 1 claimed the window "is clamped so rollback cannot extend the window". That is **false**: `computeActivationWindow()` only clamps a *future* `started_at` to now (`LicenseStateMachine.php:126-127`), and nothing persists the highest time ever seen, so moving the system clock backwards moves `now` backwards and the fixed `started_at + window` end lies further away — the unlicensed window lengthens. The gate compares the signed T0 with the **current clock** (`SignedLicenseGate.php:47-48`), so a rollback postpones T0 evaluation by the **amount of the rollback, not "up to the skew tolerance"**; the skew (`LicensePolicy.php:28`) only bounds the `GRACE`/`RESTRICTED` boundary in the state machine (`LicenseStateMachine.php:85-91`). **LIMITATION:** without a persisted high-water mark there is no anti-rollback reference at all; P-AR adds one but it is a speed bump (below).
- **Proposal P-AR (needs owner approval; no schema):** persist `max(observed now)` in a WordPress **option** (e.g. `cpms_license_last_seen`, written at most once per hour) and evaluate both the activation window and T0 against `effective_now = max(now, option)`. Pros: no table/column, works offline, removes the trivial rollback. Cons/limits: it is a **speed bump**, not DRM — anyone with database or filesystem write access can also edit the option or delete it, a restore can move it backwards (§7.5), and a mark last written **before** the real expiry can freeze below it, so it does not guarantee T0 is ever reached. It must never block the H1 operations (§1.1) even when it detects a rollback: on detection the state becomes `needs_renewal`/notice, not a data lock.

### 7.5 Stored payload trust and restore (F8, L6, L8)
- **OBSERVED:** `currentState()` reads `payload_json` from `cpms_license_state`, json-decodes it, computes the state machine from it and then applies the signed-domain binding on **every** state read (`LicenseService.php:74-82`, `decodePayload()` `:359-364`, `applyDomainBinding()` `:407-425`). The **signature** is not re-verified on this path, and `install_id` is not re-checked on this path (only inside `verifyAndStore()` at activation, `:323`). Consequences, stated honestly: (a) a row whose `payload_json` was altered is trusted as-is by the local gate — the signature is the only integrity boundary and it is not re-applied at read time; (b) `domain` **is** re-applied at read time, so a document moved to a different canonical domain yields `RESTRICTED`/`binding_mismatch` under the §5 severity rule, while `install_id` is not re-applied, so a restore onto a new install keeps the old id in the row until a refresh.
- **Separate failure outcomes (one table, K4):**

| Stored-document failure (re-verification) | Outcome |
|---|---|
| Signature fails | `INVALID` (generic reason) |
| `domain` claim mismatches the local canonical domain | `RESTRICTED` / `binding_mismatch` |
| `install_id` mismatches the current install | `INVALID` (generic reason) |
| Computed state already self-blocking and not ordinary expiration (`SUSPENDED`, `REVOKED`, `INVALID`, stale `UNREACHABLE`) | preserved unchanged (§5 severity rule) |

- **Required design behaviour (implementation prerequisite, J5):** re-verify the stored document (signature + `install_id` + `domain`) at least once per request, caching the result for that request only. The outcome **must follow the table above**, not a single catch-all: **signature failure → `INVALID`** (generic reason); **`domain`/binding mismatch → `RESTRICTED`/`binding_mismatch`**; **`install_id` mismatch → `INVALID`**; an already self-blocking computed state is **preserved** (§5). H1/M1 and §7.1a stay in force either way and the UI shows "activation/renewal required". Optional: compare against a last-known-good `verified_at`.
- **Restore onto a new install:** the backup/restore design is **not** in this repository's `main` (LIMITATION). Until it lands, treat it as an open interface and decide explicitly (owner, with that design) whether a restore preserves the licence row: (i) preserve + re-bind via a new document (recommended; the customer re-activates once), or (ii) let the restore seed a new `install_id` and require a fresh document. This design performs no schema change and adds no restore hook; §10 lists it as a stop item rather than an invented mechanism.

- Tampering (F8): editing `payload_json` so `expires_at` moves forward is detected at the next read and yields `INVALID` with H1/M1 intact (T-L28); a restored row whose `install_id` differs from the current install is detected (T-L29).
- Domain: a wrong-domain document yields `RESTRICTED`/`binding_mismatch` when the outcome was permissive, and a `SUSPENDED` document keeps `SUSPENDED` (F7, T-L30).
- Entitlements: an absent feature and a present `false` feature are off, and an unknown feature supplied as `true` is ignored (not accepted); an unknown limit can never raise a known limit; a missing known limit takes its code default, not "unlimited" (T-L31).
- Release-build gate (M2, T-L32): independent failing cases, each asserting its own `<CHECK>` and each fixture violating exactly ONE rule — `PLACEHOLDER`; `BAD_BASE64` (strict decode: a character genuinely outside the alphabet) and `NON_CANONICAL_BASE64` (round-trip: embedded whitespace or non-canonical padding) asserted **independently**, plus `PUBKEY_LENGTH`, on legacy, release-manifest and ring keys; `DUP_KEY`; `KEY_COUNT`; `RING_SIZE`; `KEY_ID_FORMAT`; `KEYLIST_MISSING` (expected, then denylist); malformed expected, then malformed denylist; `KEYLIST_OVERLAP`; `DENYLISTED_KEY` (compromised fingerprint present in the denylist) asserted **separately** in legacy, release-manifest and ring and kept distinct from `UNEXPECTED_KEY` (same key absent from the expected list, denylist empty); `RECOVERY_DENYLIST_MISSING` with the compromised fingerprint in all three locations; `MANIFEST_MISMATCH`, `VERSION_MISMATCH` and `CONTENT_POLICY` — one independently asserted negative case each.
- Online endpoint: HTTPS-only is enforced at build time — lowercase `http://`, uppercase `HTTP://` and a non-http(s) scheme are each rejected (T-L33).
- Existing-visit clinical saving (F2, L2): **T-L34** create handwriting document, **T-L35** add page, **T-L36** save page — each enumerates `LicenseStatus::VALID` plus the 7-day restricted fresh install **and covers `EXPIRING` before T0 and at/after T0 under skew** (`SignedLicenseGate.php:49-50`), calls the real path and asserts success (no `CLINIC_LICENSE_BLOCKED`); each **fails if a gate is re-added on its own path** — T-L34 on `createDocument`, T-L35 on `addPage`, T-L36 on `savePage` (§7.1a).
- Offline: a valid document with `license.server_url` empty activates and operates with no network. Real ZIP install on a clean WordPress, end to end (UNKNOWN until executed).

## 10. Schema

- **Proposal P-AR (no schema):** one WordPress **option** holds the last-seen high-water mark (§6.5). Options are not tables or columns; it still needs owner approval because it is a new persisted artifact.
- If a future need appears (reissue/rebind history, restore hook), do **not** design it here:
  - **STOPPED - OWNER DECISION NEEDED (S-1).** Question: does the license feature need persisted reissue/rebind state, or a restore hook that re-binds `install_id`? Options: (a) no schema — signed document + owner records + re-activation after a restore (recommended); (b) add a column/table in the full line first and copy the migration byte-identically to 1.0. Pros/cons: (a) zero migration risk, no shared-schema divergence; (b) enables local abuse counters and automatic re-bind, at the cost of a migration and shared-schema coupling. Recommendation: (a). Still open: the concrete workflow (§3.6.3 options (a)-(d); §3.2) and the unresolved items **U1-U7** (§3.6.3) — key generation/backup custody, issuer hosting, revocation, outage grace. Options are compared decision-ready in §3.6.3 — offline signing device / hardware security key / cloud KMS / split custody — with a MANAGER-PROPOSAL / AUTHOR-RECOMMENDATION. Risk if deferred: no signing path is approved, so D1 cannot be completed and 1.0 cannot ship a verifiable document.

## 11. Impact on the 1.0 → Full upgrade path

- The license tables are **shared** between 1.0 and the full line. This design adds no table/column, so nothing in 1.0 must be undone at upgrade; a 1.0 install with a valid document continues to verify in the full line under the same ring.
- Migration rule: new migration numbers are decided in the **full line first** and copied byte-identical to 1.0; 1.0 never creates a migration absent from the full line. This design creates **no** migration, so it is compatible by construction.
- Data-loss safety: the document, `install_id` and activation window persist across the upgrade; the offline path and the public-key ring are unchanged, so a 1.0 customer always keeps an activation route.
- **Entitlements — corrected (F9, K5).** Today `hasFeature()` returns false for an **absent** feature **and for a present feature whose value is `false`**; an unknown feature supplied as `true` is accepted (`EntitlementRegistry.php:29-37,49-53`), while `limitOf()` returns `null` for an unknown or absent limit and `allowsCreation()` then returns **true** (`:58-76`) — an unknown limit is silently *unlimited*. **Design requirement:** the set of limit keys is a closed allowlist defined in code with an explicit default per key; a document may only *narrow* those defaults; unknown keys are ignored (never treated as a grant) and logged; a missing known key takes its code default (never "unlimited"). The same rule applies to features: a document can only enable features the code knows. `LicenseSignature.php:107-117` is the signed-metadata grammar (`activation_id` bounded id, `update_rights_until` positive int) — it is **not** an entitlement extension hook; entitlements are interpreted only by `EntitlementRegistry`.
