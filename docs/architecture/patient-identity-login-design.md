### 2.7 The session proof store (R1, F1, I2)
- **Where.** WordPress keeps session data server-side per token: `wp_get_session_token()` returns the current token (<https://developer.wordpress.org/reference/functions/wp_get_session_token/>), and `WP_Session_Tokens::get()` / `::update()` read and replace that session's data (<https://developer.wordpress.org/reference/classes/wp_session_tokens/>, backed by `WP_User_Meta_Session_Tokens`). The proof entries are keys inside **that** session array — never in a cookie, never in a new table.
- **Shape.** Two maps: `cpms_mobile_proofs = { "<mobile>": { "at": "<ISO-8601 UTC>", "token_hash": "<hash>" } }` (mobiles this session proved by SMS) and `cpms_proofs = { "<clinic>:<patient>": { "binding_id": int, "verified_at": "<ISO-8601>", "at": "<ISO-8601>", "token_hash": "<hash>" } }` (bindings this session proved by NID). A fresh login starts with exactly one mobile proof — the account's own — and no binding proof. **Supported binding (N6):** `token_hash` is the plugin's own `hash('sha256', wp_get_session_token())` — WordPress's `WP_Session_Tokens::hash_token()` is marked **private** and must not be called (<https://developer.wordpress.org/reference/classes/wp_session_tokens/hash_token/>), so hashing the raw token ourselves keeps this on public API; `get_instance()`/`get()` have been public since 4.0 (INFERENCE for the target version, <https://developer.wordpress.org/reference/classes/wp_session_tokens/>).
- **Write.** A mobile proof is written by a successful OTP `verify()` for that mobile **inside this session** (the login, or a second mobile verified in the proof route, §6.2); a binding proof **only** by the two-factor route (§6.2), after its transaction commits. Before writing, the store re-reads the session and **must** find the same token still present; if it is gone the write fails closed (no proof). Each entry carries its own `at` and an assumption-free absolute lifetime, never the session's rolling expiry.
- **Read, on every request.** The gate needs (1) a live session: `WP_Session_Tokens::get_instance($uid)->get($token)` returns a non-empty session — **destroy is never trusted alone**; (2) for each proof entry, `token_hash` equal to `hash('sha256', wp_get_session_token())` recomputed on this request (N6) and `at` within the **absolute 60-minute** proof window (a constant, not a schema change); (3) a binding proof whose `binding_id` and `verified_at` match the live row, and a mobile proof for that record's `mobile`. A re-proof, a correction-close (§7.6) or a sever changes the row, so stale binding proofs die without touching storage. Any failure ⇒ level `none` (fail closed).
- **A password login writes no mobile proof (H2).** A mobile proof exists only where an OTP for that mobile was verified **in that session**; the password method establishes the account, never the mobile, so a password session holds **no** mobile proof and therefore cannot satisfy the binding gate until an OTP is given in that same session.
- **Invalidation.** Logout and every explicit `destroy`/`destroy_all()` remove the entries with the session. **Password reset and password change do not by themselves delete session metadata** — `reset_password()` documents only `wp_set_password()`/`update_user_meta` plus the `after_password_reset` and `password_reset` hooks, and `wp_set_password()` documents no session destruction (<https://developer.wordpress.org/reference/functions/reset_password/>, <https://developer.wordpress.org/reference/functions/wp_set_password/>) — so the build **must** hook both to `WP_Session_Tokens::get_instance($user_id)->destroy_all()` — a public **instance** method on the per-user manager, which destroys all sessions of that user (<https://developer.wordpress.org/reference/classes/wp_session_tokens/destroy_all/>; a version that keeps an "except this token" parameter must be called with an empty token — INFERENCE); until it does, the 60-minute proof window is the bound, and the auth cookie's own validity on a password change is INFERENCE, not verified. **WordPress limitation (I2):** `WP_User_Meta_Session_Tokens::update_session()` reads the session set and writes it back (<https://developer.wordpress.org/reference/classes/wp_user_meta_session_tokens/update_session/>), so a concurrent `destroy` can be overwritten by an `update` and a deleted verifier can reappear; this is inherent to the token manager and affects any session metadata, not only this design. Mitigation, not a fix: the write re-reads and fails closed, the gate re-validates liveness on **every** request, and no proof outlives 60 minutes — a resurrected verifier therefore carries at most the remainder of that window and only for a binding the row still agrees with. A build-time test must race `destroy` against `update` (T-L31).
- **Fallback — owner-gated.** If the token API were unavailable in the target WordPress version (4.0+ per the class changelog, so this is not expected), a transient keyed by `hash('sha256', $token)` would be the only alternative; it survives the session and is strictly weaker, so it may be used **only with explicit owner approval**, never as a default.

### 2.8 Lists, counts and writes are per proved record (I1)
A *bound* row is not an *accessible* row. Every patient-scoped read, count, aggregate and write — notification inbox, cursor, unread counts and read-marks; `/appointments/mine`, reschedule options, cancel and reschedule; visits, prescriptions, files and stream; `my-records`; portal render; and any total shown to the account — is restricted to the **intersection** of the account's active bindings and the patients proved with **both** proofs in the current session. The predicate is one helper (`PatientAccess::proved_patient_ids()`), and it is applied **inside the query** (an `IN (…)` over a validated id list), never by filtering rows after they are fetched, so a count and its list cannot diverge. **The one cross-record count (N1):** the account-wide cap (§8) is evaluated **only when every active binding of the account is session-proved**; otherwise the request receives the same uniform refusal as any other proof-required request (§6.10) — one status, one body, with no hint of which binding is unproved or how many there are, and no partial count. **LIMITATION:** an account with several bindings must therefore prove each one before it can book anything at all (an all-or-nothing rule chosen over an oracle that would reveal the unproved record's existence).

### 2.9 Accounts: staff and patient are two identities (D-1)
- **Staff account** = one WordPress user carrying staff roles and a Clinic membership; its authority comes only from RBAC/ABAC + `ScopeContext` (Organization → Clinic → Location), evaluated by the existing permission helpers.
- **Patient account** = one WordPress user whose only authority is a `cpms_patient_logins` account row plus its bindings (§1), read through the gate (§2.1); it carries no staff capability and cannot be given one by any proof.
- **Independence (D-1):** two separate WP users, two separate auth cookies and session stores, two separate permission evaluations. A person who is both doctor and patient holds **two accounts**; a staff session never becomes a patient session and a patient binding never unlocks a staff surface. A staff account may also hold a patient account **only** as a different WP user — never by adding the patient role to the staff user.
- **NID equality never merges (D-1):** the identifier is used as *proof input* (§6.2) and as *search input* (§6.12) only. No query joins two accounts by identifier, no proof transfers a permission, and two accounts that happen to hold the same identifier stay separate (test T-L34).
- **OBSERVED gap to close at build time:** today `PortalLogin::is_authorized()` `:153-174` admits a WP user without the patient role to the staff surface **only when the staff module rules grant at least one module** (`StaffPortalShell::eligible_modules()`, `:173`) and its comment names a "mixed Patient/Staff account" (`:165-171`), so mixing is possible in code. D-1 forbids it: the build must refuse the staff surface to a patient-role user **and** the patient portal to a staff-capability user, and must stop creating one user for both roles. This is a behaviour change, listed with the other dependencies in §11.2.
- **Schema: none.** Two WP users and the one approved table; if the implementation ever needs a column to flag or link the two identities, that is **STOP** for the owner.

### 2.10 Two login methods for three groups (D-2, D-3)
**Method A — identifier + SMS OTP.** The identifier arrives in the request body; the OTP goes to the mobile **already bound to that account** (patients: the record's mobile; staff: the staff mobile of §2.11). A fresh login writes **one mobile proof** and nothing else (§2.7). **Method B — identifier + fixed password.** The password is set only after the account's mobile has been verified once by OTP (D-3); before that the method is unavailable and answers with the same refusal as any other failure. **A password session may reach the binding route only to supply BOTH proofs (H2):** a fresh OTP to the mobile **in that same session** plus the identifier in the body — a password session that tries to bind without the OTP, or that carries over a proof from elsewhere, is refused with the §6.10 envelope. **What a login proves and what a binding proves are different things:** a login proves *account control* (possession of the mobile then, or the password now); it **never** proves the record, **never** writes a binding proof, **never** raises the level above `none`, and **password login never creates a binding**. Access to a patient record still needs **both** proofs in that same session (§2.7), so a patient who logs in with a password must still prove the mobile by OTP and the identifier in that session before any record is served. **Staff** (doctor, reception) are authorised by RBAC after login, not by a patient binding. **Audit (D-5):** every login attempt, success or failure, and every search writes one audit row with ids, the actor class and a closed category — never the identifier, never a free-text term. **Identical failures:** unknown identifier, wrong password, unverified mobile, unknown account and every internal fault return the §6.10 envelope — same status, same body, whether the identifier exists or not.

## 5. Account/binding state machine and the single writer (R3, F4)

**States.** Account: `pending` → `active` (first successful two-factor proof) → `closed`; `pending` → `closed` (retirement, §7.5). Binding: created `active`; `active` → `closed` (sever, restore, correction); `closed` → `active` only by a **fresh** two-factor proof (re-activation of the same row through `u_pl_bind`). No other transition exists; nothing is deleted (R5).

**The promotion moment.** A binding becomes `active` **iff** the transaction that writes all four artefacts commits. Before that commit the account is `pending` and grants nothing; after it, and only with its session proofs, `full` is possible.

**The one writer — `PatientBindingPromoter::promote()`** (new class, P6), called only from `POST /patient/link-record`, at depth 0, inside one `CpmsDb::transactional`:

| # | Write | Existing seam it must reuse |
|---|---|---|
| 1 | account row `FOR UPDATE` **first** (§8 order), then `SELECT … FOR UPDATE` the candidate patient row of the request's clinic | §8, §6.4 |
| 2 | account row `state='active'` (from `pending`) | `cpms_patient_logins` |
| 3 | clinical edge `cpms_patients.identity_id` | `PatientIdentityActivator::activate_for_new_patient()` `:77-107` (or `assert_existing_link_in_organization` `:90`) |
| 4 | identity↔user edge | `PatientIdentityService::link_user()` `:248-280`, skipped when `user_link_exists()` |
| 5 | Clinic patient↔user link | `cpms_patient_user_links` insert, pattern `PatientService.php:461-464`, `u_link_pair` `0001:97`; tolerate the existing row |
| 6 | binding row `active` + `verified_at` + `live_key` + `account_key=NULL`, or re-activate the existing row of `u_pl_bind` | `u_pl_live` is the backstop |
| 7 | one audit row (ids and closed codes only) | `AuditLogger` |

**Fail-closed:** every step verifies its own postcondition (pattern `assert_persisted_identity()` `PatientIdentityActivator.php:104`); any failure throws and the whole unit rolls back — no binding, no edge, no link, account still `pending`. The **binding proof is written after commit only** (§2.7), so a rolled-back promotion cannot leave a usable proof. Re-entry is idempotent: a second promotion for the same triple re-activates the same row.

## 6. Both proofs

### 6.1 Owner policy (final, first release)
**M1** the record's mobile must equal the OTP mobile; **M2** a record with no NID is never auto-linked; **M3** linking only in the clinic whose record matches both; **M4** limits per account/mobile/IP, never on the NID, which appears only in a request body (never URL, log, audit, rate-limit key, notification, exception); **M5** every failure returns the identical status/body/message (§6.10); **M6** on success an SMS to that mobile plus one audit row with ids/closed codes; **M7** every additional patient needs its own proof, **and its own session proof** (§2.7). **M8 (R1):** the two proofs must be given **in the same session** — an OTP session alone is account-only. Pending cap 2 per account including dependents; reception may only sever, close and correct.

### 6.2 Link-record: one clinic per proof, and the bootstrap
`POST /patient/link-record {mobile, code?, clinic_id, national_id}` — requires an **account session** and **no** binding; **shipped in P6** with the writer of §5, not with the gate (F9). The OTP is consumed **in this session** at depth 0 (§6.5) for the body's `mobile`: when that mobile is already proved in this session (the account's own, from login) `code` may be omitted, otherwise a code sent to **that** mobile must be presented — which is what lets a guardian prove a dependent whose mobile differs (M7). Then the search runs only inside the one clinic resolved for this request: `SELECT … FROM cpms_patients WHERE clinic_id = %d AND mobile = %s AND national_id = %s AND status='active' FOR UPDATE` (§6.4); `u_pat_mobile` makes that at most one row, and no row ⇒ the generic envelope. `mobile` is never taken as an identity claim: it must equal both the proved mobile and the record's mobile (M1). **Bootstrap:** a zero-binding account has no clinic, so (i) `clinic_id` comes in the body, is validated server-side as a live clinic of a live Organization, and is applied as a per-request explicit scope only — `App::replaceExplicitScope()` (`App.php:2285-2293`, `ScopeContext.php:19-41`), never to the session; (ii) the cookie stamp is written only at the next OTP issue (`begin_otp_cookie_issue()` `PatientSessionScope.php:132-142`; `record_and_maybe_stamp_cookie_token()` `:534-584`) from the account's active bindings; (iii) with no stamp the resolver falls back to "one distinct linked clinic", else `null` (`resolve_clinic_id()` `:261-277`), and every clinic-scoped route fails closed. A stamp is a snapshot and grants nothing; a resolved clinic is not a binding. `require_clinic_matching()` `:347-358` throws the clinic-name-free error.
**H1 — no identifier in SQL on the binding path.** The lookup finds the record by the **OTP-verified mobile** (unique per clinic, `0001:82`) and compares the identifier **in PHP** with `hash_equals()` (<https://www.php.net/manual/en/function.hash-equals.php>), so no identifier ever becomes part of a query string on this path. **ACCEPTED LIMITATION (H1, search):** an exact-match lookup on the plaintext column cannot avoid the identifier as a query parameter, and `CpmsDb::prepare()` inlines parameters into the query text (`CpmsDb.php:100-106`) — the database server already holds the plaintext column and operator-side query logs are outside plugin control. Mitigations: **no plugin code may log or echo SQL text, `$wpdb->last_query` or database error text** (test T-L53), and the later identifier-column encryption/digest design removes the limitation. No column is added here.

### 6.3 The only setter: a two-factor proof, in a session
A binding is one row `kind='binding'`, `state='active'`, non-NULL `verified_at`, owned by exactly the writer of §5. There is **no staff-granted path** (`verification_method` has one value; nothing staff-side sets `verified_at`), and a login alone grants nothing: the NID proved in the session, plus the mobile proved in the session, are the second half (§2.7). **One live binding per record:** `u_pl_live` enforces it across accounts; the §6.4 row lock plus a live re-read produce the friendly generic failure and remain the fallback. A second account cannot bind a bound record — same envelope. **Re-proof:** presenting both proofs again for an existing binding refreshes `verified_at`, refreshes the session entry and is idempotent; it never creates a second live row.
**A recycled holder who also holds both proofs (I4).** When a number is reassigned and the new holder can also produce the record's national ID, both proofs succeed. That is **authentication** — the two factors the owner policy requires are present — not a defect in this design; it is recorded as an accepted LIMITATION (§14) with the mitigations already here: the SMS notice to the mobile on every proof (M6), reception closing the old account and binding on report (§6.8), and the record correction that closes bindings (§7.6). **No staff grant is added, and none may be.**

### 6.4 Concurrency
`FOR UPDATE` on the candidate patient row, then re-check tenant, `status='active'`, `mobile`, `national_id`; only then write. Sever, restore-closure and correction-closure take the **same** row lock, so proof, sever and restore serialise on one row. Tests: concurrent NID edit, concurrent sever, competing accounts (T-L9, T-L25).

### 6.5 Consume runs at depth zero
The OTP consume lives **inside** `verify()`'s transaction (`OtpService.php:449`…`:527-534`) and would roll back with a failed link. The proof route therefore runs consume + attempt charge + decision in a unit that must execute at **depth 0**, checked before it runs; a nested caller fails closed with the §6.10 envelope (no consume). Depth 0 means `transactional` issues a real `START TRANSACTION`/`COMMIT` (`CpmsDb.php:282`, `:298-304`), so the consume commits before any binding row can exist. Limits: per account, per mobile across all accounts, per IP; keys hashed; the NID is never a key; `cpms_rate_limits` already exists. Tests T-L8, T-L15.

### 6.10 One failure envelope (R9, F10)
**Property (O1).** Every failure of these routes is **indistinguishable from every other failure** — bad OTP, expired OTP, NID mismatch, record mobile ≠ OTP mobile, record without NID, **unknown mobile**, **closed account**, no binding possible, duplicate race, **rate limit**, malformed body, **core-generated argument-validation and permission errors**, and any internal fault — **within the same request mode**, both **with and without** the `_envelope` parameter: one code, one message, one `data` object, one body length, whether the response is observed as the object returned by `rest_do_request()` or as the final HTTP result of real serving.

| Aspect | Value for every case above |
|---|---|
| HTTP status | `403` on the wire **without** `_envelope` (no `429`, `404`, `409`, `Retry-After`); **with** `_envelope` the transport status is `200` and this `403` travels inside the wrapper — documented: `envelope_response()` "converts the full HTTP response to data instead" (<https://developer.wordpress.org/reference/classes/wp_rest_server/envelope_response/>) |
| Body | `{"code":"CLINIC_PATIENT_PROOF_FAILED","message":"<one fixed Persian sentence>","data":{}}` |
| Coverage — before the callback | authentication is replaced through `rest_authentication_errors` (it carries `WP_Error`\|`null`\|`true`) and any early result is normalised at `rest_pre_dispatch`, a **dispatch**-level filter that therefore also runs for programmatic dispatch (<https://developer.wordpress.org/reference/classes/wp_rest_server/dispatch/>); one wrapper registers **every** plugin-owned callback (`permission_callback`, each `validate_callback`/`sanitize_callback`, the handler) so its own `\Throwable` becomes this envelope before core can shape it differently |

### 6.11 Password lifecycle (D-3, D-5)
- **Hash:** WordPress hides the password (`StaffManagementPage.php:595` relies on `user_pass` hashing) and the design uses `wp_hash_password()` — bcrypt by default since 6.8 (<https://developer.wordpress.org/reference/functions/wp_hash_password/>); the function is pluggable, so the design names the API, not an algorithm. Plaintext is never stored, logged, audited or answered; a password that a staff form generated is shown once and never re-readable.
- **Policy (PROPOSAL — owner to approve):** reuse the staff baseline already in code — at least 10 characters, at least one ASCII letter and one digit (`StaffManagementPage.php:1490-1497`, enforced `:597-601`) — for staff and patients alike; no forced rotation; no password hints.
- **Activation of method B:** only after the account's mobile has been verified by OTP once (D-3) — this rule governs the **new** identifier + password path; the legacy staff path in the next bullet keeps its existing WordPress passwords (§6.11, H3). Before that, the password method refuses with the §6.10 envelope and the only way in is method A. Setting a first password requires a **fresh** OTP in that session, so a stolen cookie cannot set one.
- **Legacy staff login stays in 1.0 (H3) — and it is not method B.** `PortalLogin` (WordPress username/email + password, `:56-66`, `:122-137`) and the administrator password paths (`StaffManagementPage.php:595-626`, `:701-708`) remain a **compatibility path**, because staff have no stored identifier and no verified mobile today (§2.11). **This legacy path does not enforce mobile verification — an ACCEPTED LIMITATION the owner has been informed of.** Method B (identifier + fixed password) is a different, new path and stays gated by first-time OTP verification for **every** group. Closing the legacy path per account once that account is verified is a **later optional item, not designed here**.
- **Reset:** identifier in the body + OTP to the **verified** mobile → new password → `WP_Session_Tokens::get_instance($user_id)->destroy_all()` (§2.7, the per-user manager) → SMS notice to the mobile → the §6.10 envelope whatever the outcome, so an unknown identifier is indistinguishable. No reset link is emailed for portal accounts; the WordPress reset key is not used on this path.
- **Mobile change:** current authentication (password or OTP) **plus** an OTP to the **new** number → sessions destroyed → SMS to the **old** number as the notice of record. Every earlier session (and therefore every proof entry) is invalid afterwards.
- **Lost phone:** reception may only sever, close or correct the record (§6.9); it never issues a way in. The person repeats first-time verification from a new number, and the old bindings stay closed until both proofs are given again.
- **Staff-side paths that bypass this gate (H3, §11.2):** an administrator setting a staff password (`StaffManagementPage.php:595-626`, `:701-708`), the WP reset-key flow (`:390-402`, `:421-450`) and the portal's lost-password link (`PortalLogin.php:75`) keep today's behaviour in 1.0; they authenticate a **staff** account, they **do not** enforce mobile verification, and they give **no** patient access — the contradiction with the activation rule above is resolved by naming them the legacy path rather than method B.

### 7.3 Restore closes every binding and recomputes keys (R5, R6)
Clearing the barrier is one manager action that destroys patient-only sessions, writes one audit row, and sets `state='closed'`, `live_key=NULL` on every binding row of the restored data, then **recomputes** `live_key` (all NULL) and `account_key` (from `wp_user_id`) for every row — a restored dump therefore carries no live key that could collide with a new binding. No restored binding is trusted; every account falls back to `none` and needs a fresh proof (both factors, new session). **Accounts, account rows and password hashes are kept; nothing is deleted.** This matches the restore rule taken read-only from `docs/architecture/backup-restore-design.md` in branch `arena/f52cec7c-doctor` at `efa0e214495b198a3a60243126212b4625e296c6`; that file does not exist in this tree at `c9771403`, so the requirement is recorded here and not claimed as met. A dump taken before those columns existed recreates the table without them (`BackupSqlDumper.php:131-141` dumps `SHOW CREATE TABLE`), so the P1 migration runs again after a restore and the hook recomputes both keys; if a row needs a key the build cannot recompute, the restore fails closed.

### 7.4 Backups and uninstall
Backups already contain every patient NID from `cpms_patients.national_id`; **encrypting the backup is a requirement of the backup work, not a fact of this tree** (UNKNOWN/LIMITATION). **Uninstall (`uninstall.php:8-20`):** unset ⇒ `return` at `:9-11`, nothing deleted, account and binding rows survive a reinstall; set ⇒ every `{prefix}cpms_%` table dropped (`:15-18`) plus two options (`:19-20`), so login rows are destroyed, **patient sessions are not explicitly destroyed** (LIMITATION — the build must add it), and patient `wp_users` are **not** deleted.

### 7.5 Retention — close and scrub, never delete (R5, F6)
The sweep is a **new** `cleanup.patient_logins` job (`App::RECURRING_JOBS` `App.php:2616-2635`; existing `cleanup.*` `:2625-2628`, `OtpCleanupHandler.php:22-25` owns only `cpms_otp_tokens`). **It deletes nothing.** It performs two state changes: (a) a **binding** older than the retention window with no active use is `closed` (`live_key=NULL`), its proof entries die with the session it belongs to; (b) a `pending` account that never proved anything after 14 days becomes `state='closed'` with `given_name`/`family_name` set to NULL **and `mobile` set to NULL** — which frees the number under `u_pl_mobile` while keeping the row, the account and the WP user intact. A closed account is terminal for access and is never deleted; a closed row is never restored to `active` without a fresh proof. **Names are scrubbed at the decision to close** (`given_name`/`family_name` → NULL), which is the revision-9 rule kept; the NID is never stored at all, so there is nothing else to scrub. **Deleting rows or WP users is not the default**; it is an **OPTION for the owner** in §16 (OQ-D2 carries the sweep's design), and no code path in this design deletes an account (§13).

### 7.6 Record correction closes the record's bindings (R4, F5)
When reception changes a record's `national_id` or `mobile` (including `PatientService::update()` and the reception correction route), or merges/deactivates the record, the **same transaction** must set every binding row of that `(clinic_id, patient_id)` to `state='closed'`, `live_key=NULL`, write one audit row, and after commit destroy the sessions of the affected users (`WP_Session_Tokens::get_instance($user_id)->destroy_all()`), because every session proof for that binding is now stale (§2.7). The patient must prove again with the new number and NID; no old binding can be reopened by possession of a number alone. A correction that only touches a name, address or phone (not the mobile, not the NID) does not close anything — the rule names the two proof fields explicitly.

## 8. Cap and lock order
Cap = 2 active appointments per account (DECIDED), counted across all patients with an **active binding** on the account (never `cpms_appointments.wp_user_id` `0001:230`, which `createByStaff` `:1935-1954` does not populate) — and evaluated **only when every one of those bindings is session-proved**; any unproved binding makes the number unanswerable, so the request gets the §6.10 envelope instead of a count (§2.8). The locking read runs in the **outermost** transaction: account row `FOR UPDATE` → `COUNT(*)` of future non-cancelled appointments. Depth guard: fail closed if nested (§6.5). **Staff bookings are exempt. Reschedule replaces the row:** `reschedule()` calls `appointments->create()` `BookingService.php:1720-1741` (status `confirmed`, `rescheduled_from` set `:1735`) and only then updates the source (`:1743-1750`), so the replacement enters the active set and a reschedule **consumes cap capacity**, counted as one by excluding rows with a non-NULL `rescheduled_to` (`:1747`). **Lock order:** account row → Organization → Clinic → Slot → Location (`:1881-1886`, `:2750-2790`); reschedule appointment-first (`:1568-1574`); `createByStaff` tenant→Slot→Location (`:1805-1935`). **Measured orders (OBSERVED):** new demand takes the tenant prefix first — Organization → Clinic → Slot → Location (`:1881-1886`); check-in takes **patient → appointment** (`VisitService.php:105` `lockPatient()` → `:112` `findForUpdate()`, comment `:107-111`: cancel/reschedule lock the same appointment row and the order is preserved); reschedule takes **appointment → tenant prefix** (`:1568-1574`, whose comment records that taking the tenant prefix first inverts check-in's pair and deadlocks). The new account lock is therefore defined as **outermost on every patient-initiated option path** (promotion, hold, reschedule request): account row → tenant prefix → patient → appointment. **No-cycle claim withdrawn:** these three orders differ by path and cannot be proven acyclic from this tree, so the build must (i) run the concurrency matrix promotion × hold × check-in × reschedule (T-L33), and (ii) apply a deterministic retry rule on deadlock — retry the whole unit up to 3 times with a bounded backoff on the engine's deadlock error, then fail with the §6.10 envelope (official guidance: always be prepared to re-issue a transaction; keep operations in a consistent order — <https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html>).

### 9.1 Counters keyed by an HMAC of the identifier (D-6)
- **Digest:** `hash_hmac('sha256', $normalized_identifier, $key)` with a 32-byte key from `random_bytes(32)` (<https://www.php.net/manual/en/function.random-bytes.php>). The counter key is `nid:<digest>`; `cpms_rate_limits` already stores an arbitrary `window_key` (`RateLimiter.php:33-40`), so **no schema change** is needed. The identifier itself never appears in a key, row, response, log or audit row.
- **Where the counter key lives (DECIDED, revision 17):** the key is read from a `wp-config.php` constant when that constant is defined (outside the dump, invisible to the admin UI and to the option table), otherwise from an option `cpms_nid_hmac_key` written with `autoload = no` and generated once at activation from `random_bytes(32)`; the `cpms_rate_limits` counter rows hold a digest, and so do the **staff identity digests**, which use a separate versioned key with the same custody rules but a different rotation rule (§2.11, H5); moving an installation to the constant later is a documented step, not a schema change.
- **Rotation:** a new key produces new digests, so rotation is done with an **overlap window**: both keys are live for one window, counters are incremented under the current key and read under either, and the retired key is dropped after the longest window has elapsed. Counter deletion already exists — `RateLimiter::cleanup()` deletes rows whose window start is older than the cutoff (`:79-87`), and the recurring cleanup job must cover the new keys.
- **Limits:** account, identifier digest, IP and OTP-send counters (the existing mobile/IP limits stay, §9); lock the account after a bounded series of failures and answer every case with §6.10.
- **LIMITATION:** a ten-digit identifier has a small space (and fewer valid checksums), so **a leaked key makes every digest guessable** — the digest is an obstacle to casual enumeration, not a secret store. Counters stay short-lived, are never a record of record, and are deleted by the cleanup job.

## 14. Security (threats)
| Threat | Mitigation | Residual (accepted) |
|---|---|---|
| **Recycled number** | An OTP-only session holds **no binding proof** (R1), and a closed account cannot be revived; reception closes the old account and frees the mobile (§6.8) | **Accepted LIMITATION (I4):** a new holder who also has the record's national ID passes both proofs and is authenticated as the patient — the owner policy's definition of access. ### 21.1 A child who already has a record (G1) — no new mechanism
- **Who binds it:** the **guardian's own account and session** (D-8). The child has no login and no session of its own; the child panel is a view inside the guardian's session, opened by the same proof §10 already requires: an OTP to the **child's own mobile on the record** plus the child's identifier in the request **body** — never in a URL, result, log, error or audit row. Nothing is inherited: the guardian's own proof never opens a child, and one child's proof never opens a sibling.
- **What the record must carry:** `mobile` is `NOT NULL` and unique per clinic (`2026_09_05_0001_initial_schema.php:60`, `:82`), so the child needs a number of its own on the record and an identifier, and the guardian must be able to receive a code on that number. If the family has one handset, the unique key blocks a second record on the same number, and that is now **DECIDED (H8 i): one patient per mobile in 1.0, child or adult — the rule stays, OQ-D1 is closed as "rule unchanged", and no schema changes.** A child can therefore be booked online only with the **child's own mobile on its record**; a child without its own mobile is registered **in person by reception**, and reception never grants access. **ACCEPTED LIMITATION (H8 iv):** someone can register another person's identifier first; because the identifier is unique per clinic (`0001:61`, `:83`) the real person must go to reception, which can only correct the record — no exception is added.
- **Unchanged protections:** no staff path grants (§6.9); identical failures (§6.10); the identifier never appears in any response, masked or not (§6.9, T-L22/T-L22b); the child's proof is per session, dies with the session and expires inside the 60-minute window (§2.7); a bound-but-unproved child contributes no list, count or hint (§2.8).

### 21.2 A child without a record: appointment request (G2) — earlier STOP, now moot
- **Moot since H8 (ii), and the absence guard stays.** Self-registration now creates the patient **record** at registration time (the code already does this: `PatientService.php:283`, `:355` call `create_record()`), so a child without a record is no longer a case the design must store: the guardian registers the child (with the child's own mobile, §21.1) and a record exists. For completeness: `cpms_appointments.patient_id` is `NOT NULL` (`:226`) with a foreign key (`:252`); `cpms_slot_holds` gained a **nullable** `patient_id` with its own foreign key in migration `0022` (`0022:12-16`, `:37`) and binds a hold to an existing record, not to a request; and no table in the schema is a request store. The earlier STOP is therefore withdrawn as moot, **but no record-less store may appear**: T-L48 keeps asserting its absence.
- **The options below are moot** (the STOP is withdrawn, §21.2) and are kept only as history: (a) a second table for requests — still a STOP, only one table is approved; (b) reception creates the record — now the design's own rule for the no-mobile child (H8 i); (c) the request stays outside the system. T-L48 keeps asserting that **no record-less store** appears.

### 21.3 What a guardian may see (G3)
- **Default panel:** the child's appointments and their status, nothing clinical. Clinical data (visits, prescriptions, files) opens only at the same `full` gate as any record — both proofs for **that child** in the guardian's session, including the record's two edges (§2.4). A child whose proof is missing shows nothing: no count, no list, no hint (§2.8).
- **Guardianship is an unverified claim — accepted LIMITATION:** the system stores no legal guardianship, so whoever holds the child's mobile code and identifier is treated as authorised, exactly as an adult holding their own. Every guardian action is audited with actor, patient id and a closed category, never the identifier (§6.6, T-L10).
- **Cap unchanged, no raise:** the account cap stays 2 (§8) and is answered only when **every** active binding is proved (§2.8), so a guardian with two children must prove both before any booking; raising it is a **STOP** and is not proposed.

### 21.4 Foreign nationals without an identifier (D-9)
- **An account, not a record:** username plus a mobile verified by OTP; method A is the mobile + OTP path (this track has no identifier to add, §2.10 method A's SMS half) and method B is the password path after first-time verification — both exactly as §2.10/§6.11, including session destruction on reset or mobile change. No national ID is asked, stored, logged or echoed on this track.
- **The username is the WordPress `user_login`** — unique by WordPress itself, so **no schema**. The design chooses a **system-generated opaque login**, following the existing pattern `wp_insert_user([ 'user_login' => $local . '-' . $suffix, … 'user_pass' => wp_generate_password( 32, true, true ) ])` (`ManagementPortalService.php:1548-1558`), shown to the person once. Justification: a user-chosen login turns registration into an existence oracle, and the alternative — refusing "taken" names — leaks the same fact.
- **No enumeration:** registration, login and password reset answer **uniformly** — no "username taken", no "unknown user", no different body for a known mobile — every refusal is the §6.10 envelope, and the counter keys use the §9.1 digest or the mobile hash, never the username in clear.
- **Never links, never reaches another person's data:** the foreign flag is an account-level usermeta marker (no column) and grants nothing; it never auto-links to an existing record (OQ-D9 §16) and opens only what the account itself created — and because a record-bearing action stops at §21.2, in 1.0 that is the account and its status, nothing else. A visit still needs a record created by reception and a binding proved with both identifiers; the no-identifier case stays owner-pending (§19).
- **STOP:** any second identifier column or table, any rule that lets the flag reach another account's data, and any username-based lookup that answers differently for a name that exists.
