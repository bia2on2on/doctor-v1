## 1. Data model (D1)

One table, `{wp_prefix}cpms_patient_logins`, **two row kinds**: an *account* row is one WP user's login identity; a *binding* row is one permission of that account over one record in one clinic. **All types declared; no generated columns (R6).**

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | `BIGINT UNSIGNED AUTO_INCREMENT` | no | PK |
| `kind` | `ENUM('account','binding')` | no | every predicate names the kind it reads |
| `wp_user_id` | `BIGINT UNSIGNED` | no | the owning account |
| `mobile` | `CHAR(11)` | **yes** | account rows only, normalised `09xxxxxxxxx`; NULL on bindings; **never nulled or freed by any path** (D-A, M1 — a number stays reserved, §6.8/§7.5) |

| `verification_method` | `ENUM('two_factor')` | **yes** | one legal value; no staff value exists |

### 2.7 The session proof store (R1, F1, I2)
- **Where.** WordPress keeps session data server-side per token: `wp_get_session_token()` returns the current token (<https://developer.wordpress.org/reference/functions/wp_get_session_token/>), and `WP_Session_Tokens::get()` / `::update()` read and replace that session's data (<https://developer.wordpress.org/reference/classes/wp_session_tokens/>, backed by `WP_User_Meta_Session_Tokens`). The proof entries are keys inside **that** session array — never in a cookie, never in a new table.
- **Shape.** Two maps: `cpms_mobile_proofs = { "<mobile>": { "at": "<ISO-8601 UTC>", "token_hash": "<hash>" } }` (mobiles this session proved by SMS) and `cpms_proofs = { "<clinic>:<patient>": { "binding_id": int, "verified_at": "<ISO-8601>", "at": "<ISO-8601>", "token_hash": "<hash>" } }` (bindings this session proved by NID). A fresh login starts with exactly one mobile proof — the account's own — and no binding proof. **Supported binding (N6):** `token_hash` is the plugin's own `hash('sha256', wp_get_session_token())` — WordPress's `WP_Session_Tokens::hash_token()` is marked **private** and must not be called (<https://developer.wordpress.org/reference/classes/wp_session_tokens/hash_token/>), so hashing the raw token ourselves keeps this on public API; `get_instance()`/`get()` have been public since 4.0 (INFERENCE for the target version, <https://developer.wordpress.org/reference/classes/wp_session_tokens/>).
- **Write.** A mobile proof is written by a successful OTP `verify()` for that mobile **inside this session** (the login, or a second mobile verified in the proof route, §6.2) — and at login the proof is written **and the session issued only when the identifier in the same body also matches the account** (§3/P4, revision 26); a binding proof **only** by the two-factor route (§6.2), after its transaction commits. Before writing, the store re-reads the session and **must** find the same token still present; if it is gone the write fails closed (no proof). Each entry carries its own `at` and an assumption-free absolute lifetime, never the session's rolling expiry.
- **Read, on every request.** The gate needs (1) a live session: `WP_Session_Tokens::get_instance($uid)->get($token)` returns a non-empty session — **destroy is never trusted alone**; (2) for each proof entry, `token_hash` equal to `hash('sha256', wp_get_session_token())` recomputed on this request (N6) and `at` within the **absolute 60-minute** proof window (a constant, not a schema change); (3) a binding proof whose `binding_id` and `verified_at` match the live row, and a mobile proof for that record's `mobile`. A re-proof, a correction-close (§7.6) or a sever changes the row, so stale binding proofs die without touching storage. Any failure ⇒ level `none` (fail closed).
- **A password login writes no mobile proof (H2).** A mobile proof exists only where an OTP for that mobile was verified **in that session**; the password method establishes the account, never the mobile, so a password session holds **no** mobile proof and therefore cannot satisfy the binding gate until an OTP is given in that same session.
- **Invalidation.** Logout and every explicit `destroy`/`destroy_all()` remove the entries with the session. **Password reset and password change do not by themselves delete session metadata** — `reset_password()` documents only `wp_set_password()`/`update_user_meta` plus the `after_password_reset` and `password_reset` hooks, and `wp_set_password()` documents no session destruction (<https://developer.wordpress.org/reference/functions/reset_password/>, <https://developer.wordpress.org/reference/functions/wp_set_password/>) — so the build **must** hook both to `WP_Session_Tokens::get_instance($user_id)->destroy_all()` — a public **instance** method on the per-user manager, which destroys all sessions of that user (<https://developer.wordpress.org/reference/classes/wp_session_tokens/destroy_all/>; a version that keeps an "except this token" parameter must be called with an empty token — INFERENCE); until it does, the 60-minute proof window is the bound, and the auth cookie's own validity on a password change is INFERENCE, not verified. **WordPress limitation (I2):** `WP_User_Meta_Session_Tokens::update_session()` reads the session set and writes it back (<https://developer.wordpress.org/reference/classes/wp_user_meta_session_tokens/update_session/>), so a concurrent `destroy` can be overwritten by an `update` and a deleted verifier can reappear; this is inherent to the token manager and affects any session metadata, not only this design. Mitigation, not a fix: the write re-reads and fails closed, the gate re-validates liveness on **every** request, and no proof outlives 60 minutes — a resurrected verifier therefore carries at most the remainder of that window and only for a binding the row still agrees with. A build-time test must race `destroy` against `update` (T-L31).
- **Fallback — owner-gated.** If the token API were unavailable in the target WordPress version (4.0+ per the class changelog, so this is not expected), a transient keyed by `hash('sha256', $token)` would be the only alternative; it survives the session and is strictly weaker, so it may be used **only with explicit owner approval**, never as a default.

### 2.8 Lists, counts and writes are per proved record (I1)
A *bound* row is not an *accessible* row. Every patient-scoped read, count, aggregate and write — notification inbox, cursor, unread counts and read-marks; `/appointments/mine`, reschedule options, cancel and reschedule; visits, prescriptions, files and stream; `my-records`; portal render; and any total shown to the account — is restricted to the **intersection** of the account's active bindings and the patients proved with **both** proofs in the current session. The predicate is one helper (`PatientAccess::proved_patient_ids()`), and it is applied **inside the query** (an `IN (…)` over a validated id list), never by filtering rows after they are fetched, so a count and its list cannot diverge. **The one cross-record count (N1):** the account-wide cap (§8) is evaluated **only when every active binding of the account is session-proved**; otherwise the request receives the same uniform refusal as any other proof-required request (§6.10) — one status, one body, with no hint of which binding is unproved or how many there are, and no partial count. **LIMITATION:** an account with several bindings must therefore prove each one before it can book anything at all (an all-or-nothing rule chosen over an oracle that would reveal the unproved record's existence).

Child-specific features and the child definition are **OUT OF 1.0 — DEFERRED TO NEXT VERSION (not designed, §23)**.
**Without an identifier — the D-9 track (§21.4, L2).** The same route with **no `national_id`** and no names writes **two** artefacts only: the WP user and the account row `state='pending'` — **no patient record, no link row, no binding**. The shape is decided by the request, never by a lookup, and the response is the same uniform `202`.
**Collisions (K2).** Three values can already be taken — the mobile on an **account** (`u_pl_mobile`), the mobile on a **record in that clinic** (`u_pat_mobile` `0001:82`), the identifier in that clinic (`u_pat_nid` `0001:83`) — and all three are **branches of one answer**: the transaction writes nothing (rollback, no WP user, no account, no record) and the response is the **same `202` body** a successful registration returns, one status, one body, one length, so the caller cannot tell which value collided, nor whose record it is. **The queue is the account table**, not `cpms_notifications` (`clinic_id NOT NULL` `0001:634`, purged by `NotifDispatchHandler.php:39-41` → `NotificationRepository::purgeArchived` `:232-242`).
**The oracle, stated honestly (ACCEPTED LIMITATION).** Whoever proves that mobile with an OTP learns the **outcome** for that number — a record now exists, or it does not — because they can then use it; that is the same owner-permitted disclosure §12B already records for `register_required`. What the design refuses is a *cheap* oracle: no response distinguishes a taken mobile from a taken identifier, none reveals a name, a clinic or a record id, every attempt is rate-limited and audited with a count (§9.1), and the collision branch is identical for an existing and a non-existing value in the *other* field. **Kept (H8 iv):** someone can register another person's identifier first; because it is unique per clinic (`0001:61`, `:83`) the real person must go to reception, which can only correct. **Consequence for retention (LIMITATION, owner-pending).** The record created here is `active` and holds the number under `u_pat_mobile` (`0001:82`, with `mobile NOT NULL` `0001:60`), and **the 14-day sweep of a never-proved `pending` account (§7.5) frees no key and nulls no mobile** (M1/N1): the number stays reserved under **both** keys in every status, and archiving that record frees nothing either (D-A). A recycled number therefore has **no designed release path** — owner-pending (C4), STOP before build; no column, no table, and the sweep still deletes nothing (§7.5). **STOP:** an identity-verifying registration (documents, staff approval, a new column or table) is not designed and needs its own owner decision.
**L1/D-A — a status change never frees a mobile (OWNER DECISION, LIMITATION, OBSERVED).** `u_pat_mobile` is `UNIQUE (clinic_id, mobile)` (`0001:82`) and ignores `status` (`:75`), so while a record exists in **any** status — `active` or `archived` — that number is taken in that clinic and a registration returns the **uniform collision** response above. Archiving, closing, severing and the 14-day scrub (§7.5) **free no key at all** — neither `u_pl_mobile` nor `u_pat_mobile` — so the number stays reserved in every status. Reception may only **correct or sever**, and neither releases or moves the number. **OWNER DECISION D-A (final, revision 21): releasing a mobile is FORBIDDEN.** A number bound to a valid account is **never** automatically freed or moved to another account, not even when the record is archived; archiving frees nothing. Any ownership change or number correction must pass an **authenticated, approved verification** — **that process is NOT designed here: STOP before build**, and no mechanism, column or table is invented. The earlier "archive the record and the number is free" sequence stays withdrawn.
**L5 — the identifier also reaches SQL on these writes.** The earlier claim that only the *search* puts the identifier into a query is corrected: the registration **writes** insert the typed identifier (the dependent-record route is deferred, §23) into `cpms_patients.national_id`, and the write path `PatientRepository::create()` (`PatientRepository.php:233-236`) → `CpmsDb::insert()` (`CpmsDb.php:195-200`) → `$wpdb->insert()` puts it into the statement, exactly as `CpmsDb::prepare()` inlines parameters (`CpmsDb.php:100-106`). The rule is unchanged and now covers them: **no plugin code may log or echo SQL text, `$wpdb->last_query` or database error text** (T-L53), and **no claim is made** that operator-side or database-server logs are under plugin control — that residue stays the accepted limitation of §6.2, removed only by the later identifier-column encryption/digest design.
**L4 — cache after a rollback.** A collision or a forced failure rolls the transaction back, but the WordPress object cache survives a rollback on a persistent backend (Redis/Memcached) and a ghost user stays resolvable (`UserCacheRollback.php:8-32`). Every rollback, collision and failure branch of the registration transaction therefore calls the existing helper `UserCacheRollback::invalidate()` (`:38`) with the created user's id, login and email, **after** the boundary has rolled back — exactly as the staff create path already does (`StaffManagementPage.php:659-675`), never a global flush. Regression test T-L58.

### 4.1 The dependent/child-record path — OUT OF 1.0 (deferred, §23)

Child-specific features and the child definition are recorded in **§23**.

### 4.2 D-C — an unfinished registration must not reserve a mobile (OWNER DECISION)
**Owner decision D-C (final, revision 21).** Person 1 starts a registration with mobile A and never confirms the OTP: their account is not completed or activated and **A must not be permanently reserved or assigned to an unverified account**. Person 2 registers with A and confirms the OTP; person 2's account is created/activated under the identity rules. If person 1 later continues, the system must tell them that the number was already verified and registered and offer two routes: **(1)** sign in with the same mobile and their **own** NID; **(2)** use another mobile whose ownership they verify. None of person 1's unverified data may cause a number takeover, an active account or access to person 2's account; responses must resist enumeration; matching and duplicate prevention must use **real identity and the system's uniqueness rules, not the mobile number alone**.
**OBSERVED in code — what an unfinished attempt writes (M7; re-read, no census claim).** An OTP request writes the following, **in this order and conditionally** (re-read for N6; no census claim): the per-mobile **quotas** are charged first (`OtpService.php:274-275`, `otp-day:`/`otp-hour:` keyed on the raw mobile, pre-checked by `peek()` at `:621-634`) and a refused charge throws **before** anything is stored, so a **denied request writes no token row**; then one `cpms_otp_tokens` row is inserted (`:296`) and `OTP_REQUEST` is audited (`:301`); the dispatch runs inside a `try/catch` (`:317-336`) that absorbs the exception, and `OTP_SENT_OK`/`OTP_SENT_FAIL` is audited either way (`:347`); the `cpms_sms_messages` row is **not unconditional** — `SmsService::sendEvent()` returns before the insert when the licence suppresses the event (`SmsService.php:186-190`) and throws on an invalid mobile (`:191-193`), and the insert is at `:254-269` — so a suppressed or failed dispatch leaves the token, the counters and an `OTP_SENT_FAIL` audit but **no** message row. Verification resolves **no** identity and issues no session (`:536-559`, §3). Nothing in this tree — and nothing in the P7 flow of §4, which writes only inside one committed transaction after a consumed OTP — writes a `wp_users` row, a `cpms_patient_logins` row, a `cpms_patients` row or a cap counter for an **unconfirmed** attempt, so under this design A is **not** reserved by person 1. **Residues (OBSERVED + OWNER-PENDING, not solved here):** (a) an unfinished attempt **consumes the shared per-mobile quotas** (hourly/daily) and can leave the cooldown/lockout state, so it can **delay person 2's** first request even though nothing is reserved (`canSend`: 60 s cooldown, 900 s after 5 bad codes) — whether that delay is acceptable against D-C is an owner question; (b) the §7.5 sweep touches only **accounts**, which an unconfirmed attempt never creates, so retention neither touches nor blocks D-C.
### 4.3 CONFLICTS WITH THE CURRENT DESIGN — OWNER-PENDING, NOT RESOLVED HERE
- **C1 — telling person 1 that the number is already registered** contradicts the identical-response rule (§2.10, §6.10) and the registration existence-oracle limitation (§4, §12B): a caller who has proved nothing would learn that the number has an account. Whether the disclosure may be gated on a fresh OTP for that number (i.e. after proving possession) is an owner decision.
- **C2 — route (1) "same mobile + own NID"** presumes person 1 owns the record; with one patient per mobile per clinic (`u_pat_mobile` `0001:82`) and one account per mobile (`u_pl_mobile`), a *different* person 1 can never satisfy it, and the design has no way to decide to whom a number belongs.
- **C3 — "match by real identity, not the mobile alone"** contradicts the uniqueness actually used: the clinic-scoped `UNIQUE (clinic_id, mobile)` and the binding lookup by **OTP-verified mobile** (§6.2); and a foreign national has **no NID** (§21.4), so on that track the mobile *is* the only uniqueness key.
- **OWNER DECISION (revision 27; recorded only, no mechanism designed).** A verified mobile is **never** automatically released or changed. A secure number-correction process with **in-person verification and Audit** is to be examined **separately**; if it blocks the 1.0 release, the limitation is documented and reported to the owner **before any feature is removed**.
- **C4 — three D-A conflicts, owner-pending (M1):** (i) the 14-day **sweep** closed a never-proved `pending` account and nulled its `mobile` — automatic release — and since registration itself consumes an OTP a `pending` account's number *is* verified, so "pending is never valid" does not hold and the sweep may not null it; (ii) **mobile change** as previously written (current authentication + OTP to the new number) would associate a number without D-A's approved verification; (iii) **closing an account and re-registering on the same number** cannot happen once no key is ever freed, so a recycled number has **no designed path** at all. All three are STOP before build.
- **C5 — how the D-9 username reaches the person (UNKNOWN, STOP before build, N7).** The foreign-national username must be **system-generated and opaque** (§21.4/M4) and the person must learn it **once**, while registration's success and collision bodies stay **byte-identical** (§4). No channel is designed or approved: a **response body** breaks that identity rule and becomes an existence oracle; an **SMS** adds a second message and a failure path; a **user-chosen** username is an enumeration oracle by construction. **STOP — owner decision**; until it is made, no test may assume a delivery channel (T-L50 takes the username "from wherever the build delivers it"). This is a delivery question only — it changes no method, no table and no column.
**Consequence:** D-C cannot be built on this architecture until the owner rules on C1-C3 — and for C3 a new identifier or uniqueness rule would be a new column/table = **STOP**. **No test rows are added for D-C**, and no code, schema or policy is changed here.

### 4.4 N2 — the initial credential of a registration-created account (SAFETY; build-time requirement)
**One sequence, and the only permitted way in (I1, revision 25).** A registration-created account follows exactly four steps, in this order:
1. **Registration creates an account that no route can authenticate.** Forbidden before step 2, absolutely: **method B** (§2.10 identifier + fixed password) through any surface, `wp-login.php` username/email + password, any REST cookie/nonce request as that user, WordPress **application passwords**, and the WordPress **lost-password / reset-key** flow (which would otherwise set a password without ever proving the mobile). Nothing else is issued.
2. **The activation event is the first successful method A** — the account's mobile verified by an OTP **in the request body** together with the matching identifier (§2.10, §6.2, D-3; on the D-9 track the identifier is the username, §21.4). It is the **only** authentication permitted before activation, and it **is** the activation: `OTP login is not "authentication before activation" — it is the activation itself`, and it issues the patient session (a login proves account control and binds nothing, §2.10).
3. **Only a method-A session established with BOTH proofs may set the fixed password** — **any such session after activation, not one particular session object** (I2, revision 26): method A again with a **fresh** OTP and the matching identifier in the same session (§6.11), so if the first session expires a later two-proof OTP session may finish the first-password setup; never a carried-over proof, and no admin, staff, reset or mobile-only path may do it (§2.9).
4. **Method B works only after step 3** — identifier + fixed password, and it still grants no record access without both proofs (§2.10, §6.2).
**And nothing else changes:** every route named in step 1 stays forbidden until step 2 has happened, and step 3 is reachable from **any method-A session of the same account established with both proofs after activation** — the first one or a later one — but **never** from a session of a different account, a pre-activation state, a session without both proofs, a staff-issued reset or a mobile/OTP alone; step 4 cannot be reached without step 3. **An undisclosed ordinary random password does not satisfy this**: it is a working credential the moment it exists, it can be reset into a known one, and possession of neither factor is required. **OBSERVED:** the only staff-enrolment precedent in this tree does exactly that (`wp_insert_user` with `wp_generate_password( 32, true, true )`, `ManagementPortalService.php:1551-1558`), so it is **not** a model for this account.
**Why this is not solved here.** WordPress exposes per-surface controls, all documented — `wp_authenticate_username_password()` authenticates through `wp_check_password()` (pluggable, `check_password` filter) and is wrapped by the `wp_authenticate_user` filter (<https://developer.wordpress.org/reference/functions/wp_check_password/>, <https://developer.wordpress.org/reference/functions/wp_authenticate_username_password/>); reset is gated by `allow_password_reset` / `wp_is_password_reset_allowed_for_user()` (<https://developer.wordpress.org/reference/hooks/allow_password_reset/>); application passwords by `wp_is_application_passwords_available_for_user` (<https://developer.wordpress.org/reference/hooks/wp_is_application_passwords_available_for_user/>), and `reset_password()` writes a new password with no veto of its own (<https://developer.wordpress.org/reference/functions/reset_password/>) — but **no single documented mechanism makes a WordPress account non-authenticatable**, and the stored-value half (an initial value no plaintext can match) is **not a documented feature**. **MANAGER-PROPOSAL (owner may object) — BUILD-TIME REQUIREMENT, no longer a blocking STOP:** the **P7 build PR must contain a mechanism** that satisfies this requirement and **must prove it with T-L59**; the mechanism is chosen **in that PR** from the documented hooks cited above and **reviewed by two readers** before merge. If, at build time, **no supported mechanism exists**, the build **STOPs and asks the owner** — the requirement is never dropped and T-L59 is never weakened.
## 5. Account/binding state machine and the single writer (R3, F4)

**States.** Account: `pending` → `active` (first successful two-factor proof) → `closed`; `pending` → `closed` (retirement, §7.5). Binding: created `active`; `active` → `closed` (sever, restore, correction); `closed` → `active` only by a **fresh** two-factor proof (re-activation of the same row through `u_pl_bind`). No other transition exists; nothing is deleted (R5).

**The promotion moment.** A binding becomes `active` **iff** the transaction that writes all four artefacts commits. Before that commit the account is `pending` and grants nothing; after it, and only with its session proofs, `full` is possible.

**The one writer — `PatientBindingPromoter::promote()`** (new class, P6), called only from `POST /patient/link-record`, at depth 0, inside one `CpmsDb::transactional`:

| # | Write | Existing seam it must reuse |
|---|---|---|
| 1 | account row `FOR UPDATE` **first** (§8 order), then `SELECT … FOR UPDATE` the candidate patient row of the request's clinic | §8, §6.4 |
| 2 | account row `state='active'` (from `pending`) | `cpms_patient_logins` |
| 3 | clinical edge `cpms_patients.identity_id` | `PatientIdentityActivator::activate_for_new_patient()` `:77-107` (or `assert_existing_link_in_organization` `:90`) |
| 4 | identity↔user edge | `PatientIdentityService::link_user()` `:248-280`, skipped when `user_link_exists()` |
| 5 | Clinic patient↔user link | `cpms_patient_user_links` insert, pattern `PatientService.php:461-464`, `u_link_pair` `0001:97`; tolerate the existing row |
| 6 | binding row `active` + `verified_at` + `live_key` + `account_key=NULL`, or re-activate the existing row of `u_pl_bind` | `u_pl_live` is the backstop |
| 7 | one audit row (ids and closed codes only) | `AuditLogger` |

**Fail-closed:** every step verifies its own postcondition (pattern `assert_persisted_identity()` `PatientIdentityActivator.php:104`); any failure throws and the whole unit rolls back — no binding, no edge, no link, account still `pending`. The **binding proof is written after commit only** (§2.7), so a rolled-back promotion cannot leave a usable proof. Re-entry is idempotent: a second promotion for the same triple re-activates the same row.

## 6. Both proofs

### 6.1 Owner policy (final, first release)
**M1** the record's mobile must equal the OTP mobile; **M2** a record with no NID is never auto-linked; **M3** linking only in the clinic whose record matches both; **M4** limits per account/mobile/IP, never on the NID, which appears only in a request body (never URL, log, audit, rate-limit key, notification, exception); **M5** every failure returns the identical status/body/message (§6.10); **M6** on success an SMS to that mobile plus one audit row with ids/closed codes; **M7** every additional patient needs its own proof, **and its own session proof** (§2.7). **M8 (R1):** the two proofs must be given **in the same session** — an OTP session alone is account-only. Pending cap 2 per account including dependents; reception may only sever, close and correct.

### 6.2 Link-record: one clinic per proof, and the bootstrap
`POST /patient/link-record {mobile, code?, clinic_id, national_id}` — requires an **account session** and **no** binding; **shipped in P6** with the writer of §5, not with the gate (F9). The OTP is consumed **in this session** at depth 0 (§6.5) for the body's `mobile`: when that mobile is already proved in this session (the account's own, from login) `code` may be omitted, otherwise a code sent to **that** mobile must be presented — which is what lets an account holder prove a dependent whose mobile differs (M7). Then the lookup runs only inside the one clinic resolved for this request: `SELECT … FROM cpms_patients WHERE clinic_id = %d AND mobile = %s AND status='active' FOR UPDATE` — **the identifier is not in the query** (K1); the row's `national_id` is compared with the body's value **in PHP** using `hash_equals()` (<https://www.php.net/manual/en/function.hash-equals.php>), and `u_pat_mobile` makes the match at most one row, so no row or a failed comparison ⇒ the same generic envelope. `mobile` is never taken as an identity claim: it must equal both the proved mobile and the record's mobile (M1). **Bootstrap:** a zero-binding account has no clinic, so (i) `clinic_id` comes in the body, is validated server-side as a live clinic of a live Organization, and is applied as a per-request explicit scope only — `App::replaceExplicitScope()` (`App.php:2285-2293`, `ScopeContext.php:19-41`), never to the session; (ii) the cookie stamp is written only at the next OTP issue (`begin_otp_cookie_issue()` `PatientSessionScope.php:132-142`; `record_and_maybe_stamp_cookie_token()` `:534-584`) from the account's active bindings; (iii) with no stamp the resolver falls back to "one distinct linked clinic", else `null` (`resolve_clinic_id()` `:261-277`), and every clinic-scoped route fails closed. A stamp is a snapshot and grants nothing; a resolved clinic is not a binding. `require_clinic_matching()` `:347-358` throws the clinic-name-free error.
**H1 — no identifier in SQL on the binding path.** The lookup finds the record by the **OTP-verified mobile** (unique per clinic, `0001:82`) and compares the identifier **in PHP** with `hash_equals()` (<https://www.php.net/manual/en/function.hash-equals.php>), so no identifier ever becomes part of a query string on this path. **ACCEPTED LIMITATION (H1, search):** an exact-match lookup on the plaintext column cannot avoid the identifier as a query parameter, and `CpmsDb::prepare()` inlines parameters into the query text (`CpmsDb.php:100-106`) — the database server already holds the plaintext column and operator-side query logs are outside plugin control. Mitigations: **no plugin code may log or echo SQL text, `$wpdb->last_query` or database error text** (test T-L53), and the later identifier-column encryption/digest design removes the limitation. **The same limitation applies to the registration writes of §4** (L5; the dependent-record route is deferred, §23), where the typed identifier is inserted into the record. No column is added here.

### 6.3 The only setter: a two-factor proof, in a session
A binding is one row `kind='binding'`, `state='active'`, non-NULL `verified_at`, owned by exactly the writer of §5. There is **no staff-granted path** (`verification_method` has one value; nothing staff-side sets `verified_at`), and a login alone grants nothing: the NID proved in the session, plus the mobile proved in the session, are the second half (§2.7). **One live binding per record:** `u_pl_live` enforces it across accounts; the §6.4 row lock plus a live re-read produce the friendly generic failure and remain the fallback. A second account cannot bind a bound record — same envelope. **Re-proof:** presenting both proofs again for an existing binding refreshes `verified_at`, refreshes the session entry and is idempotent; it never creates a second live row.
**A recycled holder who also holds both proofs (I4).** When a number is reassigned and the new holder can also produce the record's national ID, both proofs succeed. That is **authentication** — the two factors the owner policy requires are present — not a defect in this design; it is recorded as an accepted LIMITATION (§14) with the mitigations already here: the SMS notice to the mobile on every proof (M6), reception closing the old account and binding on report (§6.8), and the record correction that closes bindings (§7.6). **No staff grant is added, and none may be.**

### 6.4 Concurrency
`FOR UPDATE` on the candidate patient row, then re-check tenant and `status='active'` in the query and `mobile` and `national_id` **in PHP** (`hash_equals()`); only then write. Sever, restore-closure and correction-closure take the **same** row lock, so proof, sever and restore serialise on one row. Tests: concurrent NID edit, concurrent sever, competing accounts (T-L9, T-L25).

### 6.5 Consume runs at depth zero
The OTP consume lives **inside** `verify()`'s transaction (`OtpService.php:449`…`:527-534`) and would roll back with a failed link. The proof route therefore runs consume + attempt charge + decision in a unit that must execute at **depth 0**, checked before it runs; a nested caller fails closed with the §6.10 envelope (no consume). Depth 0 means `transactional` issues a real `START TRANSACTION`/`COMMIT` (`CpmsDb.php:282`, `:298-304`), so the consume commits before any binding row can exist. Limits: per account, per mobile across all accounts, per IP; keys hashed; the NID is never a key; `cpms_rate_limits` already exists. Tests T-L8, T-L15.

### 6.8 Shared and recycled mobile (DECIDED + R1)
`u_pat_mobile` UNIQUE (`0001:82`) and `mobile NOT NULL` (`0001:60`): a shared number serves **one patient per clinic** in this release; several per clinic is next-version (§18). One account per mobile (`u_pl_mobile`) means a second person on that number **cannot register** — no second account, record or binding — and closing an account frees nothing, while the record keeps the number (`u_pat_mobile`, L1/D-A). What a new holder of a recycled number *does* obtain is the old account's **account-only** session, and record access only if they also hold the record's identifier: that is the accepted two-proof case of §6.3, unchanged by this paragraph. **Recycled number, exactly:** the new holder receives the old account's SMS and can open an **account-only** session (§2.7) — and nothing else: no binding, no binding proof, every record route `none`, identical envelopes (§6.10). Handling a recycled number is **not designed (M1).** **No code path may null, free or reassign `u_pl_mobile` or `u_pat_mobile`.** Reception may only **close** the account (`state='closed'`, sessions destroyed, one audit row) or sever/correct a record — **a state change that grants nothing**, never a reassignment of the old bindings, which stay `closed` with `live_key=NULL` — and because the account's `mobile` is **not** cleared, that number stays unavailable under `u_pl_mobile` too, while the record keeps it under `u_pat_mobile` in every status. A second person on that number therefore gets nothing but the **uniform collision** response of §4: the new holder can create **no** account, **no** record and **no** binding with it. **D-A (final):** a number bound to a valid account is never automatically freed or moved, and any ownership change or number correction needs an authenticated approved verification that is **not designed — STOP before build**. The earlier "reception closes the account and the new holder registers" story is **withdrawn** and listed as owner-pending (C4). Identities carry a non-unique `normalized_mobile` (`0019:36-51`, deliberately not UNIQUE) and no NID (`0018:27-36`), so no matcher can join two people by number at Organization level.

### 6.9 Staff actions: sever, close, correct — never grant
Reception creates records via `ReceptionPortalController.php:183-188` → `PatientService::create` `:370-378` → `create_record` `:379-496`, can set a checked NID, and can **correct** record data (which closes bindings, §7.6). It can **sever** a binding: `UPDATE … SET state='closed', live_key=NULL` + one audit row + `WP_Session_Tokens::get_instance($user_id)->destroy_all()` — **a state change, never a DELETE, and never a change to the account row or to `wp_users`**. It can **close** an account (account row `state='closed'`, sessions destroyed); the WP user and its password hash stay. **Closing never deletes an account or a user** (§7.5). Reception search returns `searchView()` `:831-844` via `search()` `:245-257` and `to_search_view()` `:823-825`, and today that row carries a **masked** NID (`:839`) while the staff read `get()` `:264-273` returns `staffView()` with the **raw** field (OBSERVED). **Both change at P2 (O2):** the NID leaves **every** response projection of patient data — patient and staff, raw and masked — so **reception can no longer see even a masked NID in results**; correction stays a request body (§7.6), this design adds only `login_state` to `searchView()`, and **no reveal endpoint, capability or parameter exists**. Until the staff change lands, no patient-side route is opened (§11.1). **"Pending registrants must first visit reception" stays removed** — a `pending` account proves itself through §6.2.

### 6.10 One failure envelope (R9, F10)
**Property (O1).** Every failure of these routes is **indistinguishable from every other failure** — bad OTP, expired OTP, NID mismatch, record mobile ≠ OTP mobile, record without NID, **unknown mobile**, **closed account**, no binding possible, duplicate race, **rate limit**, malformed body, **core-generated argument-validation and permission errors**, and any internal fault — **within the same request mode**, both **with and without** the `_envelope` parameter: one code, one message, one `data` object, one body length, whether the response is observed as the object returned by `rest_do_request()` or as the final HTTP result of real serving.

| Aspect | Value for every case above |
|---|---|
| HTTP status | `403` on the wire **without** `_envelope` (no `429`, `404`, `409`, `Retry-After`); **with** `_envelope` the transport status is `200` and this `403` travels inside the wrapper — documented: `envelope_response()` "converts the full HTTP response to data instead" (<https://developer.wordpress.org/reference/classes/wp_rest_server/envelope_response/>) |
| Body | `{"code":"CLINIC_PATIENT_PROOF_FAILED","message":"<one fixed Persian sentence>","data":{}}` |
| Coverage — before the callback | authentication is replaced through `rest_authentication_errors` (it carries `WP_Error`\|`null`\|`true`) and any early result is normalised at `rest_pre_dispatch`, a **dispatch**-level filter that therefore also runs for programmatic dispatch (<https://developer.wordpress.org/reference/classes/wp_rest_server/dispatch/>); one wrapper registers **every** plugin-owned callback (`permission_callback`, each `validate_callback`/`sanitize_callback`, the handler) so its own `\Throwable` becomes this envelope before core can shape it differently |
| Coverage — core-generated errors | core argument validation runs in the **dispatch cycle before** `rest_request_before_callbacks`, and permission refusals inside `respond_to_request()` after it (the dispatch page documents `dispatch()` as the entry that matches and calls and lists `rest_pre_dispatch`; the exact position of validation is **INFERENCE** from the documented hook lists and is asserted by T-L32 — <https://developer.wordpress.org/reference/classes/wp_rest_server/dispatch/>, <https://developer.wordpress.org/reference/classes/wp_rest_server/respond_to_request/>); every such response is normalised at `rest_request_after_callbacks` and, on serving, at `rest_post_dispatch`, which receives the **final response object** (<https://developer.wordpress.org/reference/hooks/rest_post_dispatch/>) |
| Internal faults | also `403` + the same body: the wrapper catches `\Throwable` and logs category + ids server-side only (never the NID, never an input value); there is **no** 503 exception on these routes |
| Coverage — serving and `_envelope` | `rest_post_dispatch` normalises the final response on `serve_request()`; `_envelope` is then applied by `serve_request()` itself through `envelope_response()` (documented as used by `serve_request()` and batch), so the assertion is on the envelope's own `status`/`body` fields, not the transport status; `rest_do_request()` "route[s] internal requests through `WP_REST_Server`" and returns the response object (<https://developer.wordpress.org/reference/functions/rest_do_request/>), so `rest_post_dispatch` and `_envelope` are **not** on that path — **INFERENCE** from the documented entry points, asserted by T-L32(a) |
| Differences | **none by design** — the code, message, `data`, header set and body length are constants; no field, length, count or branch varies with the input (no timing claim is made: only the response is uniform, and no counter is exposed) |
| Outside plugin control | **LIMITATION:** a fatal inside a third-party callback on a WP hook that fires before, around or after dispatch (`rest_authentication_errors`, `rest_pre_dispatch`, `rest_request_before_callbacks`, `rest_request_after_callbacks`, `rest_post_dispatch`, `rest_pre_echo_response`, `rest_envelope_response`), or an output-rewriting filter that runs after ours, cannot be enveloped by plugin code; T-L32 records the residue |
| JSONP refusal (K3) | `serve_request()` checks the JSONP callback (`wp_check_jsonp_callback()`) and filters `rest_jsonp_enabled` **before** dispatch and before the hooks and envelope of this table, and answers an invalid or disabled callback with **its own `400`** — a core response, not this envelope (<https://developer.wordpress.org/reference/classes/wp_rest_server/serve_request/>; OBSERVED in the documented flow, hook order **INFERENCE**). It depends on the request's JSONP parameters only, happens before authentication and before any lookup, and therefore **cannot distinguish identifiers**: T-L32 asserts identity-independence in that mode, not a plugin `403` and not an enveloped `200` |

Success returns `200` with `{"code":"OK","message":"…","data":{"binding_id":…}}`. The audit row is written for both outcomes with ids and closed codes; the server log carries a category code and ids, never the NID or any input value.

### 6.11 Password lifecycle (D-3, D-5)
- **Hash:** WordPress hides the password (`StaffManagementPage.php:595` relies on `user_pass` hashing) and the design uses `wp_hash_password()` — bcrypt by default since 6.8 (<https://developer.wordpress.org/reference/functions/wp_hash_password/>); the function is pluggable, so the design names the API, not an algorithm. Plaintext is never stored, logged, audited or answered; a password that a staff form generated is shown once and never re-readable.
- **Policy (PROPOSAL — owner to approve):** reuse the staff baseline already in code — at least 10 characters, at least one ASCII letter and one digit (`StaffManagementPage.php:1490-1497`, enforced `:597-601`) — for staff and patients alike; no forced rotation; no password hints.
- **Activation of method B:** only after the account's mobile has been verified by OTP **once** — and that first successful **method A is the activation event itself**, the single authentication permitted before activation, which then issues a session that may set the password — and **any later method-A session with both proofs may also do it if the first expired** (§4.4 step 3, revision 26) (D-3) — in 1.0 this governs the **patient** path only, because staff identifier login is deferred (§22); the legacy staff path in the next bullet keeps its existing WordPress passwords. Before that, the password method refuses with the §6.10 envelope and the only way in is method A (§4.4). Setting a first password requires a **fresh** OTP in that session, so a stolen cookie cannot set one.
- **Legacy staff login stays in 1.0 (H3) — and it is not method B.** `PortalLogin` (WordPress username/email + password, `:56-66`, `:122-137`) and the administrator password paths (`StaffManagementPage.php:595-626`, `:701-708`) remain a **compatibility path**, because staff have no stored identifier and no verified mobile today (§2.11). **This legacy path is the ONLY staff login in 1.0 and it does not enforce mobile verification — an ACCEPTED LIMITATION the owner has been informed of and has now decided (revision 18).** It is rate-limited by the existing `LoginRateLimiter` (`src/Infrastructure/Security/LoginRateLimiter.php`), whose ceiling is enforced after the core handlers at priority 100 (after `wp_authenticate_username_password`/`wp_authenticate_email_password` at 20 and `wp_authenticate_spam_check` at 99, before the restore barrier at `PHP_INT_MAX`), replacing both `WP_User` and `WP_Error` results at the ceiling so a correct password cannot bypass the limit. Method B (identifier + fixed password) is a different, new path and stays gated by first-time OTP verification for **every** group. **Later optional, not designed here (S4):** a forced password change at a staff member's first login, and closing the legacy path per account once that account is verified.
- **Reset:** identifier in the body + OTP to the **verified** mobile — for the D-9 account the **username takes the identifier's place** (§21.4, N4) → new password → `WP_Session_Tokens::get_instance($user_id)->destroy_all()` (§2.7, the per-user manager) → SMS notice to the mobile → the §6.10 envelope whatever the outcome, so an unknown identifier is indistinguishable. **Before a first password exists, reset is not a weaker route than first setup:** it needs the **same two proofs** — identifier in the body + OTP to the verified mobile — and it then sets the first password from that two-proof session; it never bypasses step 3 (§4.4). No reset link is emailed for portal accounts; the WordPress reset key is not used on this path.
- **Mobile change — process not designed, STOP before build (M1).** The rule of revisions 15-21 (current authentication **plus** an OTP to the new number, then sessions destroyed and an SMS to the old number) would associate a number with an account **without** D-A's authenticated approved verification; it is **withdrawn** and listed as owner-pending (C4). Until the owner decides, no account and no record may have its `mobile` reassigned or nulled, and no test may assert a change.
- **Lost phone (M1):** reception may only sever, close or correct the record (§6.9) and never issues a way in; the person **cannot** self-move to a new number, because that is exactly the ownership change D-A reserves for an approved verification that is **not designed (STOP)**. Whether a person who has lost their number can be served at all is **OWNER-PENDING** (C4) — no mechanism is invented here.
- **Staff-side paths, and the K4 correction:** an administrator's password paths (`StaffManagementPage.php:595-626`, `:700-708`), the WP reset-key flow (`:390-402`, `:421-450`) and the portal's lost-password link (`PortalLogin.php:75`) keep today's behaviour in 1.0 for **staff** accounts, do **not** enforce mobile verification and give **no** patient access (H3). **They are not staff-only today:** because `MANAGEABLE_ROLES` (`:50-56`) includes `ROLE_PATIENT`, the same screen can create a patient-role account and set its password — so the owner rule of §2.9 (K4) is a **build-time requirement**, denial-tested (T-L56), not a claim about current code.

### 7.3 Restore closes every binding and recomputes keys (R5, R6)

### 7.5 Retention — close and scrub, never delete (R5, F6)
The sweep is a **new** `cleanup.patient_logins` job (`App::RECURRING_JOBS` `App.php:2616-2635`; existing `cleanup.*` `:2625-2628`, `OtpCleanupHandler.php:22-25` owns only `cpms_otp_tokens`). **It deletes nothing.** It performs two state changes: (a) a **binding** older than the retention window with no active use is `closed` (`live_key=NULL`), its proof entries die with the session it belongs to; (b) a `pending` account that never proved anything after 14 days becomes `state='closed'` and its `given_name`/`family_name` are set to NULL, keeping the row, the account and the WP user. **M1/D-A correction:** the sweep **must not null `mobile` and must not free, re-key or move any number** — the revision-21 reasoning ("a `pending` account is never valid, so nulling may stand") is **withdrawn**, because registration itself consumes an OTP and a `pending` account's number is therefore verified; the sweep's treatment of unproved accounts and **any** retention or cleanup of them is **OWNER-PENDING — STOP before build** (C4). This table still never stores the NID (§1). A closed account is terminal for access and is never deleted; a closed row is never restored to `active` without a fresh proof. **Names are scrubbed at the decision to close** (`given_name`/`family_name` → NULL), which is the revision-9 rule kept; the NID is never stored at all, so there is nothing else to scrub. **Deleting rows or WP users is not the default**; it is an **OPTION for the owner** in §16 (OQ-D2 carries the sweep's design), and no code path in this design deletes an account (§13).

### 7.6 Record correction closes the record's bindings (R4, F5)
**M1 correction:** reception may **not** change a record's `mobile` — that is the ownership change D-A reserves for an approved verification that is not designed (**STOP**, C4) — so this rule covers `national_id` and other corrected fields plus merge/deactivation. When reception changes a record's `national_id` (including `PatientService::update()` and the reception correction route), or merges/deactivates the record, the **same transaction** must set every binding row of that `(clinic_id, patient_id)` to `state='closed'`, `live_key=NULL`, write one audit row, and after commit destroy the sessions of the affected users (`WP_Session_Tokens::get_instance($user_id)->destroy_all()`), because every session proof for that binding is now stale (§2.7). The patient must prove again with the number **held on the record** — unchanged, because a number change is STOP (C4) — and the corrected NID; no old binding can be reopened by possession of a number alone. A correction that only touches a name, address or phone (not the mobile, not the NID) does not close anything — the rule names the two proof fields explicitly.

## 8. Cap and lock order
Cap = 2 active appointments per account (DECIDED), counted across all patients with an **active binding** on the account (never `cpms_appointments.wp_user_id` `0001:230`, which `createByStaff` `:1935-1954` does not populate) — and evaluated **only when every one of those bindings is session-proved**; any unproved binding makes the number unanswerable, so the request gets the §6.10 envelope instead of a count (§2.8). The locking read runs in the **outermost** transaction: account row `FOR UPDATE` → `COUNT(*)` of future non-cancelled appointments. Depth guard: fail closed if nested (§6.5). **Staff bookings are exempt. Reschedule replaces the row:** `reschedule()` calls `appointments->create()` `BookingService.php:1720-1741` (status `confirmed`, `rescheduled_from` set `:1735`) and only then updates the source (`:1743-1750`), so the replacement enters the active set and a reschedule **consumes cap capacity**, counted as one by excluding rows with a non-NULL `rescheduled_to` (`:1747`). **Lock order:** account row → Organization → Clinic → Slot → Location (`:1881-1886`, `:2750-2790`); reschedule appointment-first (`:1568-1574`); `createByStaff` tenant→Slot→Location (`:1805-1935`). **Measured orders (OBSERVED):** new demand takes the tenant prefix first — Organization → Clinic → Slot → Location (`:1881-1886`); check-in takes **patient → appointment** (`VisitService.php:105` `lockPatient()` → `:112` `findForUpdate()`, comment `:107-111`: cancel/reschedule lock the same appointment row and the order is preserved); reschedule takes **appointment → tenant prefix** (`:1568-1574`, whose comment records that taking the tenant prefix first inverts check-in's pair and deadlocks). The new account lock is therefore defined as **outermost on every patient-initiated option path** (promotion, hold, reschedule request): account row → tenant prefix → patient → appointment. **No-cycle claim withdrawn:** these three orders differ by path and cannot be proven acyclic from this tree, so the build must (i) run the concurrency matrix promotion × hold × check-in × reschedule (T-L33), and (ii) apply a deterministic retry rule on deadlock — retry the whole unit up to 3 times with a bounded backoff on the engine's deadlock error, then fail with the §6.10 envelope (official guidance: always be prepared to re-issue a transaction; keep operations in a consistent order — <https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html>).

### 9.1 Counters keyed by an HMAC of the identifier (D-6)
- **Digest:** `hash_hmac('sha256', $normalized_identifier, $key)` with a 32-byte key from `random_bytes(32)` (<https://www.php.net/manual/en/function.random-bytes.php>). The counter key is `nid:<digest>`; `cpms_rate_limits` already stores an arbitrary `window_key` (`RateLimiter.php:33-40`), so **no schema change** is needed. The identifier itself never appears in a key, row, response, log or audit row.
- **Where the counter key lives (DECIDED, revision 17):** the key is read from a `wp-config.php` constant when that constant is defined (outside the dump, invisible to the admin UI and to the option table), otherwise from an option `cpms_nid_hmac_key` written with `autoload = no` and generated lazily on first use as `bin2hex(random_bytes(32))` (a 64-character hex string) when the row is absent or empty; the `cpms_rate_limits` counter rows hold a digest; the **staff identity digest** of §22 (deferred) would use a separate versioned key under these same custody rules; moving an installation to the constant later is a documented step, not a schema change.
- **Rotation:** a new key produces new digests, so rotation is done with an **overlap window**: both keys are live for one window, counters are incremented under the current key and read under either, and the retired key is dropped after the longest window has elapsed. Counter deletion already exists — `RateLimiter::cleanup()` deletes rows whose window start is older than the cutoff (`:79-87`), and the recurring cleanup job must cover the new keys.
- **Limits:** account, identifier digest, IP and OTP-send counters (the existing mobile/IP limits stay, §9); lock the account after a bounded series of failures and answer every case with §6.10.
- **LIMITATION:** a ten-digit identifier has a small space (and fewer valid checksums), so **a leaked key makes every digest guessable** — the digest is an obstacle to casual enumeration, not a secret store. Counters stay short-lived, are never a record of record, and are deleted by the cleanup job.

| Threat | Mitigation | Residual (accepted) |
|---|---|---|
| **Recycled number** | An OTP-only session holds **no binding proof** (R1), and a closed account cannot be revived; reception may close the old account (a staff action, never a transfer), the record keeps the number in every status, and **D-A forbids any automatic release** (§6.8, §4/L1) | **Accepted LIMITATION (I4):** a new holder who also has the record's national ID passes both proofs and is authenticated as the patient — the owner policy's definition of access. ### 21.4 Foreign nationals without an identifier (D-9)

Every earlier sentence describing a different method set (mobile+OTP as the body key, "no login beyond password plus OTP recovery") is **deleted**; **MANAGER-PROPOSAL (pending owner approval):** the exact request shapes and that the username — not the mobile — is the submitted key.
