## 4. Encryption, signatures and custody

| Element | Design |
|---|---|
| Setup | Generate encryption keypair and Ed25519 signing keypair. Site retains encryption public key and protected signing secret; doctor's offline, versioned key bundle holds encryption private/public key and signing public key, key IDs and format. The signing secret is deliberately host-resident under D-C, not included in backups. **Salt, nonce and AEAD:** while the backup archive payload uses `secretstream` (which manages its own internal stream nonces; see `Backup` below), the offline key bundle is encrypted as a single AEAD message: each bundle creation or key rotation generates a **fresh random salt** (`SODIUM_CRYPTO_PWHASH_SALTBYTES` = 16 bytes via `random_bytes()`, never reused across bundles) and derives a unique 256-bit wrapping key from the independently held recovery phrase with Argon2id (`SODIUM_CRYPTO_PWHASH_ALG_ARGON2ID13`; [PHP `sodium_crypto_pwhash`](https://www.php.net/manual/en/function.sodium-crypto-pwhash.php)). Encrypt the entire bundle (signing public key, encryption keys, key IDs and format) using **`XChaCha20-Poly1305-IETF` AEAD** ([PHP `sodium_crypto_aead_xchacha20poly1305_ietf_encrypt`](https://www.php.net/manual/en/function.sodium-crypto-aead-xchacha20poly1305-ietf-encrypt.php); [libsodium AEAD](https://doc.libsodium.org/secret-key_cryptography/aead)) with a **fresh 24-byte (192-bit) random nonce** per bundle, binding cleartext version, salt, bounded KDF parameters and nonce as AEAD additional data. Nonce reuse is prevented both because every bundle derives a fresh key from a fresh salt (one encryption per key) and because `XChaCha20-Poly1305-IETF`'s 192-bit nonce permits random generation without practical collision limits ([libsodium AEAD](https://doc.libsodium.org/secret-key_cryptography/aead)); short-nonce AEAD modes with random nonces are disallowed, and any future multi-message AEAD under one key must use a strict monotonic counter or rekeying. Verify bundle AEAD authentication before trusting any metadata or signing key; wrong phrase, altered metadata/ciphertext or failed authentication rejects the bundle and restore without substituting any archive key. Securely deliver and test the bundle/phrase off-host; no phrase or key in logs. |
| Backup | Per backup generate a fresh random 256-bit data key, seal it to the encryption public key, and encrypt the archive with `crypto_secretstream_xchacha20poly1305` chunks requiring `TAG_FINAL` and no trailing bytes. **Stream nonce strategy:** `secretstream` generates a fresh 24-byte header per stream on `init_push` and manages its own internal per-chunk nonces/counters and rekeying, preventing nonce reuse, chunk reordering, duplication or truncation ([PHP `secretstream_init_push`](https://www.php.net/manual/en/function.sodium-crypto-secretstream-xchacha20poly1305-init-push.php); [libsodium `secretstream`](https://doc.libsodium.org/secret-key_cryptography/secretstream); [libsodium AEAD](https://doc.libsodium.org/secret-key_cryptography/aead)). Hash the exact canonical versioned header plus ciphertext incrementally with SHA-256; sign a domain-separated header+digest using Ed25519 detached signature over ciphertext, not a whole archive in memory ([sealed box](https://www.php.net/manual/en/function.sodium-crypto-box-seal.php) gives confidentiality/integrity, not sender identity; [sign](https://www.php.net/manual/en/function.sodium-crypto-sign-detached.php); [verify](https://www.php.net/manual/en/function.sodium-crypto-sign-verify-detached.php)). |
| Restore | Manager supplies independently trusted bundle and phrase. Verify the signature over the bounded, streamed archive first with the bundle's signing public key, before decrypting. Do not trust an embedded signing key. Then unwrap data key, authenticate every chunk and final tag and manifest/digests. Require sodium functions at both ends; absent extension = fail closed, install supported sodium, no plaintext fallback. |
| Lifecycle | Create local encrypted output directly; do not write decrypted SQL or another plaintext dump file to disk. During restore feed authenticated chunks from memory directly into the existing empty target CPMS tables under the closed barrier (no staging tables); attachments use private temporary files as specified in §5. LIMITATION: database and private attachment storage may contain plaintext identity data; deletion of files on SSDs, snapshots, swap, DB logs and backups is not guaranteed. Protect these at least as strongly as the live site; disable application/driver query-parameter logging for restore and exclude identity values from restore logs, errors and reports. Database-managed journals and host snapshots remain subject to the live-site protection and retention policy. Reuse secretstream concepts from existing envelope (`src/Infrastructure/Backup/BackupEncryptionEnvelope.php:69-85`) but migrate S3 to mirror the same signed encrypted container, not a host-key-encrypted plaintext local backup. Legacy import requires separate explicitly approved migration and old key; no silent downgrade. |
| Loss and rotation | Loss of bundle or phrase makes protected private key unavailable unless separately secured recovery copies exist. Loss of signing public key prevents trusted verification; loss of signing secret prevents new signatures, not old verification. Rotate keys with explicit manager enrollment and new bundle; retain prior bundles to read historical backups. Losing only the host must not lose the doctor's backup and bundle. Live-host compromise can forge future signatures; show signed sequence/time and request manager confirmation against independent records. Anti-rollback is manual, not automatic. |

## 5. Restore, barrier, audit and rollback

| Phase | Required behavior |
|---|---|
| Preflight & lock | Fresh independent WP + compatible CPMS install, no clinical data and no conflicting CPMS users beyond a designated recovery manager; reject collisions, unsupported prefix, multisite or incompatible schema/engines. **Definition of "write" (before-any-write guarantee):** any creation, modification or deletion in `{prefix}cpms_*` tables, `wp_users`/`wp_usermeta`, uploaded/private attachment files or storage directories, or persistent `wp_options` (including any durable barrier, journal or plugin option). **No cleanup inside validation:** if a prior failed attempt left `RESTORE_FAILED_NEEDS_TEARDOWN` set, refuse immediately with zero writes; cleanup is a separate explicit operation (below), never executed inside preflight or validation of a new attempt. **REQUIREMENT (DB schema-version gate):** before any write — unlike `src/Application/Backup/BackupService.php:283-319,349-363`, which drops `cpms_*` tables and applies `db.sql` without comparing DB schema versions — restore must compare the dump's CPMS DB schema version and applied `cpms_schema_migrations` ledger (`src/Migrations/MigrationRunner.php:25,167-188`) against the target install and **refuse on mismatch with a clear error message** naming both versions (until the owner decides §10 OQ2, both older and newer dumps are refused fail-closed). Read-only preflight validates full detached signature, decrypts/verifies every secretstream chunk, `TAG_FINAL` and manifest in bounded memory, paths, per-file digests, schema census, mappings, disk space and version matrix. **Strict order before first persistent write:** (1) pass read-only preflight, (2) acquire the **non-persistent** session-scoped restore lock (`SELECT GET_LOCK(name, 0)` on a DB-qualified name, [MySQL Locking Functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html), matching `src/Bootstrap/App.php:2657`; held only in server memory, writes zero rows/options/files, auto-releases on session end; MariaDB behavior is INFERENCE tested at build time), (3) quiesce/drain active writers (INFERENCE: multi-worker PHP-FPM drain verified by build-time test), and (4) run the **final emptiness and schema-version recheck** (`0` rows in all `{prefix}cpms_*` tables except `cpms_schema_migrations`, no non-manager CPMS WP users, `0` files in target storage roots, clean allowlisted options; fresh WP allows only the designated recovery manager). Any failure through step (4) releases `GET_LOCK` and aborts with **zero persistent writes**. Reject unrecognized identifiers; use structured table records and allowlisted identifiers, not blind text prefix replacement. |
| Close barrier | **Only after** `GET_LOCK`, writer drain and the final emptiness recheck succeed, perform the first persistent write: set a durable non-autoloaded `wp_options` restore barrier (`RESTORE_IN_PROGRESS`, outside `src/Infrastructure/Backup/BackupSqlDumper.php:113-118` and excluded from option import) and confirm read-back before writing any CPMS row, WP user or attachment file. **Justification:** once target mutation starts, non-persistent `GET_LOCK` disappears on session disconnect or server restart ([MySQL Locking Functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html)); a durable `wp_options` barrier is therefore required before target data/file writes to enforce crash-safe fail-closed isolation across all PHP workers. Missing/unreadable barrier state during recovery fails closed. Deny patient access, login, staff/API/CLI/cron/jobs and file delivery; allow only the separately authenticated, capability-checked recovery-manager route. Protect files outside webroot; bootstrap and server-level bypass coverage is a release blocker. |
| Direct load (no staging tables) | **MANAGER DECISION:** create **zero** persistent or temporary staging tables and perform **no** `CREATE TABLE`, `DROP TABLE` or `RENAME TABLE` swap (backup/restore adds no tables or columns). Under `GET_LOCK` and the closed barrier, decrypt secretstream chunks in memory and load validated records **directly into the existing empty target `{prefix}cpms_*` tables** (`src/Migrations/MigrationRunner.php:33-120`) via strict-checked DML, with no plaintext SQL or dump file on disk; `{prefix}cpms_schema_migrations` is verified equal in preflight and preserved in place rather than re-inserted, while all other `{prefix}cpms_*` tables start at `0` rows. Check every query, metadata read, write and commit (`src/Infrastructure/Db/CpmsDb.php:17-25,109-119` OBSERVED defaults to soft false; `src/Application/Backup/BackupService.php:348-360` ignores results). Record each restore-created target WP user ID, destination file path and allowlisted option key in the non-sensitive `wp_options` restore journal (not a new table) before creating/moving it. Create target WP users with fresh IDs and explicit mapping, keeping all restored WP accounts and preserving each imported password hash without treating it as plaintext or rehashing it ([wp_check_password](https://developer.wordpress.org/reference/functions/wp_check_password/); [wp_insert_user](https://developer.wordpress.org/reference/functions/wp_insert_user/) hashes new-user `user_pass`, so do not pass a saved hash there; verify supported WP/pluggable verifiers and reject unsupported hash formats). Remap `L` columns and known live embedded references while loading **every** restored patient-login binding as **closed** (grants nothing; closing never deletes or removes accounts); for `cpms_patient_logins` (`doctor-v1` PR #2 OPEN INTERFACE), also close bindings and recompute/clear any application-maintained key columns defined there. Fail missing source WP user rows, target collisions or unsupported data; preserve `H` IDs; mark outbound rows `RESTORE_CANCELLED` (§3); import role capabilities without foreign sessions/privileges. Decrypt each attachment to a private temporary file outside webroot, verify its SHA-256 digest, move it to its final private location under the barrier, and rewrite storage root settings. |
